## 术语说明：判断层与后端是解耦的

本文中「**判断层**」「**决策模型**」指的是**角色**，不是某个具体实现。正文里出现的 `Kev` 是写作时的默认指代，**实际可按后端切换**——见下方「后端选型」。所有设计（状态机、抽取 prompt、召回、整理层）都不依赖具体后端。

## 后端选型

| 后端 | 形态 | 零样本可用性 | 部署 | 定位 |
| --- | --- | --- | --- | --- |
| **Jev** | 云端 API，闭源 | ✅ 可直接用 | 只需 API key | **v0.1 使用** |
| **Laya-421M** | 本地，Apache-2.0，ModernBERT 双向编码器 | ❌ **必须微调**（基础 ckpt 0.362 < 多数类基线 0.461） | **约 1GB 内存，CPU/Mac 均可** | **本地首选** ⭐️ |
| **Kev-4B** | 本地，Apache-2.0，Qwen3.5 decoder + LoRA | ⚠️ 相对可用（0.797） | 32GB Mac 或 GPU | 本地备选 |

**为什么本地首选从 Kev 改成 Laya**：

1. **体积差 10 倍**（421M vs 4B）。这不是速度问题，是**部署门槛**问题——"装完就能用"和"先确认你有 32GB 内存"是两种产品。
2. **延迟差约 20 倍**（38ms vs 721ms）。但要说清楚：**在我们的场景里这个优势有限**——普通写入可按轮次/阶段合批，明确维护需及时处理；巡检可离线，延迟要求须按触发类型实测。它真正的价值是**解锁"更高频的判断"**（比如每轮对话都判一次），以及召回精排可以做多轮。
3. 两者**都必须微调才有竞争力**（Kev 也要），所以"Laya 零样本差"不是否决理由，只是"必须微调"的另一种说法。
4. 代价：Laya 的中文实测不强（MASSIVE 上 zh-CN 0.62/0.63），且 `score` 原语最弱（SST-5 仅 0.372）——**而我们的召回精排正好要用 score**。这一条必须靠自建评测集实测。

**所以后端选择不是拍板，而是要用评测回答的问题**：v0.1 用 Jev 跑通链路并建立评测协议，然后用独立训练数据分别微调 Laya 和 Kev，在相同冻结测试集上比较。测试输入及其派生日志不得回流训练。

## 0. 设计目标

实现可追溯的记忆维护核心，并比较规则、生成式 LLM 与 Jev 在同一执行器中的质量与成本。memoir 提供宿主编排参考；claude-mem 提供生命周期捕获、待处理事件和分层检索参考。Git 负责版本与历史，范围和维护语义由核心校验；不预先声称首创或优于现有实现。

## 2. 整体架构：四层 + 一个贯穿的判断层

```text
输入接入：CLI / 结构化事件 / 后续宿主适配
    ↓
接收记录 → 抽取事实与维护意图 → 所属范围内候选
    ↓
规则 / LLM / Jev → 提案与确定性检查 → 单范围完整提交
    ↓
可见范围的 ref@commit 集合 → 当前有效视图 / 冲突提示
    ↓
简短索引 → 条目详情 → 必要的来源与历史
```

明确维护及时处理，普通内容在轮次/阶段边界合批；Stop 是一轮回答结束，SessionEnd 才是会话结束。生命周期定义与来源见补充设计 §3。接收成功、已应用、待审、失败分别报告，异步执行不构成捕获完整性的证明。

启动/恢复/压缩后提供小份背景；新任务及相关操作按需召回。变更或范围切换后刷新视图，不要求每轮调用模型。首版由核心与 CLI 重放，完整 hooks、常驻服务和 `/dream` 是后续产品方向。

判断器通过显式配置选择；网络或响应失败保留接收事件，重试复用身份，不静默切换后端。多范围读取与单范围写入见补充设计 §5，当前源码分支不是记忆范围。

## 3. 判断层：决策模型插在六个点

**关键分工原则**：**Kev 不生成文本，只做选择。** 所以"抽取事实"和"整合成文"必须靠 LLM，"分类/判定/排序"交给 Kev。

| # | 判断点 | 题型 | 谁做 | 为什么 |
| --- | --- | --- | --- | --- |
| 1 | 从对话抽取候选事实 | 生成 | **LLM** | 需要生成能力，Kev 做不到 |
| 2 | 门控：这条值不值得记 | noul / 规则 | LLM 主 + **Kev 复核** | memoir 的 prompt 已用规则做得很好了，Kev 用于兜底 |
| 3 | 分类：归到哪个 taxonomy path | choice | **Kev** | 固定分类空间、可微调、零成本 |
| 4 | **冲突判定**：与已有记忆是什么关系 | choice | **Kev** ⭐️ | new / duplicate / supersede / update / contradict |
| 5 | 重要性打分 | score | **Kev** | 用于优先级排序 |
| 6 | 召回精排：候选与查询的相关性 | score + noul | **Kev** ⭐️ | 批量打分，每题独立 |

第 4 和第 6 是 Kev 的主场，也是现有实现完全没有的部分。

### 为什么不让 LLM 全包了？

memoir 的做法是**一次 haiku 调用同时完成抽取 + 分类**（输出 `<path>\t<fact>`），然后绕过底层库的分类器链，端到端快 25–30 倍。这个优化很漂亮，但它有三个代价，而 Kev 正好补上：

| 问题 | LLM 一次性做完 | 用 Kev 做判断层 |
| --- | --- | --- |
| 判断漂移 | 每次调用可能给出不同分类 | 仍需测重复调用与排列敏感性 |
| 成本 | 记录实际调用成本 | 云端调用或本地推理均计入端到端成本 |
| 校准 | confidence 是自报的，不可信 | **可微调 + 可实测校准** |
| 离线 | 依赖 API 可用性 | 完全离线 |
| 冲突判定 | 使用相同操作集合和校准预算作对照 | choice 题型 + 候选进 state，可靠性由评测验证 |

**待验证的方向是**：LLM 负责抽取与整合，适合的结构化判断交给决策模型；质量、稳定性与成本收益以对照实验为准。

## 4. 状态机设计 ⭐️

维护操作的语义需要显式定义，并通过逐步事件序列验证：

### 4.1 状态定义

| 状态 | 含义 | 召回时 | 怎么进入 |
| --- | --- | --- | --- |
| `active` | 当前有效 | ✅ 参与 | 默认 |
| `superseded` | 被新记忆取代（**必须有指向者**） | ❌ 不参与，但可溯源 | 写入时判 `supersede` |
| `patched` | 部分过期，已打补丁 | ✅ 参与（用补丁后的内容） | 写入时判 `update` |
| `contradict` | 与另一条互相矛盾，未判定 | ⚠️ 两条都召回并提示冲突 | 写入时判 `contradict` |
| `pending`（提案状态） | 变更证据或置信度不足，等待复核 | 提案不参与；原有效条目继续可用 | 进入 staging |
| `expired` | 到期规则或环境证据证明已失效 | ❌ 不参与普通召回 | **巡检**核实 |
| `archived` | 人工归档 | ❌ 不参与 | 人工 |

### 4.2 状态存在哪

**条目状态存在 entry 的 YAML frontmatter 里，待审提案另存 staging。** 每条事实使用独立 ID 与作用域；taxonomy 只是分类，不是唯一键。下面是条目格式示例：

```yaml
---
id: mem_20260923_153045_a3f2
scope: project/example
status: active              # ← 状态机字段
created: 2026-09-23T15:30:45Z
last_verified: 2026-09-23T15:30:45Z   # ← 巡检用
verified_by: kev-4b@1.13
confidence: 0.87            # ← Kev 给的置信度
taxonomy: preferences.coding.style
tags: [coding, style]
supersedes: []              # ← 它取代了谁
superseded_by: null         # ← 谁取代了它
related_keys: [...]         # ← 姐妹条目（跨分类）
source: session/2026-09-23#turn-42    # ← 溯源
---

（正文）
```

### 4.3 状态转移表

| 当前状态 | 事件 | Kev 判定 | 目标状态 | 动作 |
| --- | --- | --- | --- | --- |
| （不存在） | 新事实写入 | `new` | `active` | 新建 entry + commit |
| `active` | 写入相似事实 | `duplicate` | `active` | 不新建，只更新 `last_seen` |
| `active` | 写入新事实 | `supersede` | 旧→`superseded` / 新→`active` | 新旧条目与双向引用在**一次完整 commit** 中更新 |
| `active` | 写入补充事实 | `update` | `patched` | 保留变更历史，明确当前有效值；普通召回仅输出补丁后的内容 |
| `active` | 写入矛盾事实 | `contradict` | 双方→`contradict` | 加冲突标记，**进 `pending` 队列等人裁决** |
| `active` | Kev 置信度不足 | —— | 原条目保持 `active` | 创建 `pending` 提案，等人工 review，不隐藏原条目 |
| `active` | 巡检：到期或有环境变化证据 | `expired` | `expired` | 保存证据引用；只有时间变旧或检查失败时保持原状态并待复核 |
| `contradict` | 人工裁决 | —— | 胜者 `active` / 败者 `superseded` | 记录裁决理由 |
| 任意 | 明确撤回 | —— | `archived` | 记录撤回原因与来源，原事件重放不能恢复该事实 |
| 任意 | 人工归档 | —— | `archived` | 不再召回 |

冲突判定先核对作用域、时间与明确修正关系；本轮要求和长期偏好不自动构成冲突。变更执行器验证引用、作用域、合法转移及事件幂等；写入串行化，提交前检查基准版本，读者只读取完整提交。失败恢复不能留下半完成的取代关系。

### 4.4 三条铁律

1. **保留可追溯历史。** 业务失效通过状态表达，历史查询仍可读取旧内容；这不代表物理擦除，也不允许旧来源重放自动恢复已撤回事实。
2. **低置信度不覆盖当前事实。** 变更留在待审队列，原有效条目继续可用。评测同时检查错误抑制与过期事实误用。
3. **状态转移必须可溯源。** 每次转移都在 commit message 里写清"由什么触发、Kev 判定什么、置信度多少"。

### 4.5 状态机治不了的那一类

状态机的驱动力是**写入事件**——有新东西来才触发重判。但有一类过期**没有写入事件**：项目路径改了、工具版本升级了、外部依赖废弃了。那条记忆本身没错，只是世界变了，它会安静躺在 `active` 里烂掉。

→ **需要基于证据的巡检。** `last_verified` 用于决定何时复核；路径检查、配置变化或明确到期规则提供判定依据。模型无法仅凭旧内容知道外部世界是否变化，证据缺失或检查失败时不得直接标为失效。研究原型提供可注入时钟与环境证据的最小入口，完整整理层（§7）后置。

**状态机 + 定期巡检，缺一不可。**

## 5. 记忆抽取设计

### 5.1 核心可以照抄 memoir 的 prompt

“沉默是默认”仅适用于新增事实抽取。撤回、纠正等维护指令另行识别，不得作为难负例直接丢弃。

我读了 `memoir/hooks/prompts/stop_capture.tmpl` 全文，它的设计非常成熟，值得直接借鉴：

**① 「沉默是默认」原则**

> Your default answer is NOTHING. Empty output. Zero lines. Silence.
> 绝大多数轮次没有持久事实，**沉默是正确的、预期的、高质量的结果——它不是失败**。

**② memoir 的四道持久性检查**（参考实现的抽取规则）

1. 这个事实是否 DURABLE（一周/一月后仍相关）？
2. 未来会话是否真会受益，还是显而易见/短暂的？
3. 是否**不能**从代码、git log、已有文档里发现？
4. 一位资深工程师会写进 onboarding 笔记，还是会翻白眼？

**③ 明确的正向触发器**（覆盖沉默默认）

- 长期规则 / going-forward 指令：`from now on…`、`always X`、`never X`、`every time…`
- 明示偏好：`I prefer…`、`use X over Y`、`don't use…`
- 本轮**已解决**的决策——**抓 why 不只抓 what**；跳过明确推迟的（TBD / pending review）
- 本轮浮现的项目事实
- 非显然的技术知识：不变量、坑、隐藏约束

**④ 明确的排除清单**

- 常规问答、代码阅读、"show me X" 请求
- 当场解决的一次性调试
- **工具调用及其输出**（那是机制不是事实）
- 已有内容的复述、礼貌闲聊、只针对本轮的反馈
- **飞行中的讨论 / 未解决的决策**

**⑤ 一个精妙的边界**（原文特别强调）

> 以**反馈形式**表达的长期规则（"don't do X anymore"、"from now on do Y"）是 DURABLE——**要捕获**。判断标准是规则是否适用于未来轮次，而不是它是否以纠正的形式表达。

**⑥ 输出格式**

```
<taxonomy-path>[<TAB><fact>]
```
- 每行 `路径<TAB>事实`，**0–6 行**
- 路径严格遵守 `^[a-z][a-z0-9_]*(\.[a-z0-9_]+){2}$`（三层、小写下划线、**禁止连字符**）
- **不匹配的行会被下游静默丢弃**——这个正则校验在 `stop.sh` 里也硬编码了一遍，防模型跑偏
- 一个事实可挂多个路径（逗号分隔，最多 2 个），用于真正跨类目的事实
- 无前言、无解释、无"未找到事实"消息——只有行，或完全空

以上 prompt、排除项及输出格式是 memoir 的参考，不是 gitev 的接收契约。工具结果可作为允许留存的证据；未完成状态可作为带任务/时间条件的信息。生活记忆不套用工程笔记门槛，短期跨会话内容可带有效期；纠正与撤回不被新增事实门控丢弃。gitev 采用结构化校验并明确报告格式错误，不静默丢弃。详见补充设计 §2、§6。

### 5.2 分类体系换成「个人记忆」版

memoir 的 fallback taxonomy（下面是它的原版，是个人向的，很适合你）：

```
profile.{personal,professional}      身份、人口统计、职业、教育、技能、位置
preferences.{coding,tools,work,...}  编辑器、语言、框架、AI 模型、工作方式
workflow.{coding,devops}             测试、分支、评审、部署、版本
context.project.{stack,repo,infra,database,cicd,standards}
relationships.{family,friends,professional}
goals.{career,education,projects,financial}
experience                           过往工作、里程碑、决策
knowledge.technical
behavior.work                        日程、习惯
routine.daily                        站会、仪式
```

**注意它用的是「3 层固定深度」**（`category.subcategory.type`），这带来两个好处：召回时可以按层级渐进展开（§6），以及分类空间固定 → **正适合 Kev 的 choice 题型微调**。

### 5.3 与 Kev 的接法

```
对话转录
   ↓
[LLM 一次调用] 抽取 + 初步分类（照抄 memoir 的 prompt 结构）
   ↓  输出 candidates: [{path, fact, confidence?}]
   ↓
[Kev 批量判定]  ← 这是新增的
   ├─ bucket:    choice  → 六个分类（含 skip）
   ├─ overlap:   choice  → new / duplicate / supersede / update / contradict
   ├─ importance: score  → 1–5
   └─ verify:    noul   → 这条是用户明确确认的事实，还是会话中的推测/转述？
   ↓
按 §4.3 状态转移表执行
```

**注意 Kev 的问题之间是隔离的**（每个问题只看 state、看不到其他问题的答案），所以上面四个问题必须**对同一个 state 独立成立**，不能设计级联逻辑。这正好符合我们的需求。

## 6. 召回设计

`memoir` 的 `memory-recall` skill 设计密度极高，直接借鉴：

### 6.1 六种模式 + 默认单发

| 模式 | 何时用 | 动作 |
| --- | --- | --- |
| `[mode=get]` | 查询点名了确切路径 | 直接 get |
| **`[mode=fast]`** | **默认** | 一次 `summarize --depth 3` + 一次批量 `get`，**2 次 CLI 调用 + 2 轮推理** |
| `[mode=drill]` | 仅当 >1000 条 且查询宽泛 | 按 L1→L2 逐层下钻，**每层一次批量调用** |
| `[mode=flat]` | 仅当 >1000 条 且单一 glob | 一次 `summarize --keys` |
| `[mode=blame]` | 溯源问题（"我什么时候决定的"） | git blame |
| `[mode=diff]` | 跨提交/分支问题 | git diff |

**硬上限：一次只返回 5–7 条**，绝不更多。**原始输出不做任何综合**——不分组、不复述、不加"bottom line"、不加 markdown 标题。调用它的父代理负责渲染。

### 6.2 成本启发式（很实用）

> "一次没用上的召回成本很低；漏掉一个记住的偏好成本很高。"
> → **默认开启召回**，只有机械的单符号查找、一次性草稿、用户明确关闭时才跳过。

### 6.3 召回分两阶段，Kev 管第二阶段

| 阶段 | 手段 | 哲学依据 |
| --- | --- | --- |
| 粗召回 | `git log --grep`（commit message）+ 全文索引 | **grep-over-rag**：对结构化、人类可读的文件，按名字/关键词推理优于不透明向量匹配。Claude Code 明确拒绝了向量搜索（它调 `ls()` 然后推理哪些文件相关） |
| 精排 | **Kev**：把查询 + 5–10 条候选塞进 state，`score` 打相关度 + `noul` 过时效 | 语义相关性判断 |

### 6.4 精排的两个工程约束（来自 Jev 失效模式实测）

1. **候选顺序会改变结果** → 用 `/v1/systemone/permute` 先测敏感度；敏感就多轮随机化取平均（代价是延迟 ×N）
2. **候选数量会改变判断**（IIA 违背：加一个无关选项，已有选项 log-odds 从 +0.38 掉到 +0.11）→ **每次精排固定候选条数**

## 7. 整理层：Auto Dream（垃圾回收器）⭐️

这是你提的"引导模型去整理仓库级别的记忆"，Claude Code 的 Auto-Dream 有完整公开设计可直接迁移。

### 7.1 四道门（**按计算成本从便宜到贵排序，任一不过立即退出**）

| # | 条件 | 检查成本 |
| --- | --- | --- |
| 1 | 距上次整理 ≥ 24 小时 | 时间戳比较（最便宜） |
| 2 | 累积 ≥ 5 个会话 | 扫文件列表 |
| 3 | 距上次扫描 ≥ 10 分钟 | 时间戳比较 |
| 4 | 获取文件系统锁（防并发） | 需要加锁 |

Claude Code 的实现里，锁文件防止两个实例同时对同一个项目做梦；失败自动回滚。

### 7.2 四阶段

| 阶段 | 做什么 | Kev 能加速的地方 |
| --- | --- | --- |
| **Orient（定向）** | 读索引 + 扫主题文件的**标题和目录**，**不读全文** | —— |
| **Gather（采集）** | **grep 优先，不是读全文**。定向搜：用户纠正过的点、明确保存（"remember this"）、跨会话重复主题、重要决策 | —— |
| **Consolidate（整合）** | 相对时间戳转绝对日期；**删除被明确矛盾的事实**；合并重复观察为规范条目；**解决不同会话的冲突结论** | ⭐️ **两两冲突检测**——这是典型的 choice 判定，且要跑很多对，Kev 便宜 |
| **Prune（修剪）** | 重写主题文件；重建索引（在上限内）；删除不再相关的条目 | ⭐️ 判"这条还成立吗"（noul） |

**实测数据**（Claude Code）：小测试 1 分 19 秒，把 280 行索引减到 142 行；913 个累积会话约 8–9 分钟后台完成。

### 7.3 安全约束（必须照搬）

- **做梦期间对项目代码只读**，只能写记忆文件
- **沙箱在记忆目录内**，不能写到别处
- **失败回滚**
- 顺序化包装，防重叠运行

### 7.4 三层记忆层级

| 层 | 内容 | 加载策略 |
| --- | --- | --- |
| **L1 索引** | 约 150 字符的指针清单，**有行数上限** | 始终在上下文 |
| **L2 主题文件** | 实际知识 | 按需加载 |
| **L3 会话日志** | 原始转录 | **从不全文重读，只 grep 特定标识符** |

> 原设计里有一句话很到位：**"dream 是这个架构的垃圾回收器。没有它，L2 会变陈腐和自相矛盾，L1 会膨胀到没用，L3 会变得无法导航。"**

### 7.5 入口形态

- **手动**：`/dream` 命令 + "consolidate my memory files" 这类自然语言触发
- **自动**：四道门都过时，由 SessionStart hook 提示或后台触发

## 8. git 存储结构

```
<记忆仓库>/
├── .git/
├── index.md                 # L1：索引（有行数上限）
├── entries/                 # L2：记忆条目
│   ├── mem_20260923_153045_a3f2.md
│   └── ...
├── topics/                  # L2：主题聚合（dream 维护）
│   ├── preferences-coding.md
│   └── ...
├── staging/                 # 待人工 review（pending / contradict）
├── logs/                    # L3：按日期的 append-only 日志
│   └── 2026/09/2026-09-23.md
└── taxonomy.yaml            # 分类体系（可自定义覆盖）
```

**存储模型**：采用一事实一条目的结构，借鉴条目文件和 Git 历史的可追溯性：

- **一个独立 `memory_id` ↔ 一个 entry 文件**；同一 taxonomy 可容纳多个不同作用域或不同内容的事实。
- 后续变更通过 ID 定位条目，形成补丁或状态转移，并保留历史；提案尚未应用时只进入 staging。

**commit message 规范**（照抄 gitmemo 的思路）：

```
[<taxonomy-l1>] <动作> <对象>

<1-3 句摘要>
status: active → superseded
by: kev-4b@1.13 (confidence 0.91)
trigger: session/2026-09-23#turn-42
```

## 9. MVP 配置形态

独立 CLI 的首版配置如下；不自动读取宿主模型凭据。

| 配置项 | 使用条件 | 说明 |
| --- | --- | --- |
| 通用 LLM | 自然语言摄入、LLM 判断对照 | base_url、model、api_key；只支持 Responses，先非流式自包含请求 |
| Jev | Jev 判断轨道 | `TYPESAFE_API_KEY` 与独立适配器 |
| 记忆仓库 | 所有存储操作 | 本地独立仓库；远程同步后置 |
| 所属/允许范围 | 写入/读取 | 稳定项目与设备 ID；绑定与组合见补充设计 §5 |
| 模型与策略版本 | 模型操作与评测 | 能固定则固定，未知版本明确记录；无校准语义操作待审 |
| 生命周期与读取预算 | 批次/召回及评测 | 调用方显式传入；不依赖后台服务 |

缺少所需模型配置或服务失败时明确报错；不调用模型的历史读取等命令不要求凭据。后续宿主可传入已抽取的结构化事件，但不作为首版配置复用机制。

**为本地后端预留的接口**：判断层后端抽象成一个 `judge` 接口（输入 `state` + `questions`，输出 typed answers）。v0.1 的实现是 `JevJudge`（HTTP 调 `api.typesafe.ai`）。

后续接入时，两种后端的适配成本差别很大：

| 后端 | 适配成本 | 说明 |
| --- | --- | --- |
| **Kev** | **低（`base_url` 级别）** | API 与 TypeSafe System One **完全兼容**，官方 `typesafe-sdk` 改 `base_url` 即可 |
| **Laya** | **中（需写适配器）** | **API 不兼容** System One，需把 `state + questions` 翻译成 Laya 的调用形式。好在三种原语语义一致（`choice` / `score` / `noul` + `criteria` 结构），适配器不复杂，但不是零成本 |

**这也意味着 `judge` 抽象不能偷懒做成 "只换 base_url"** —— 要按能力（三种原语 + 概率 + 置信度）抽象，而不是按某个具体 API 的形状抽象。

**⚠️ 一个必须处理的后端差异**：Laya 的 `confidence` 字段**在三种原语之间语义不一致**——`choice`/`score` 用归一化熵 `1 − H(p)/log(k)`，`noul` 用 `max(p, 1−p)`。同样是"一边 0.9 的二选一"，`noul` 报 0.90 而 `choice` 只报 0.53。而我们的设计**同时**用 `choice` 做分类/冲突判定、用 `noul` 做写入门控，还要在这上面算阈值。所以：**接入任何后端时，第一步都是把它的 `confidence` 语义校准成同一套定义**（建议统一成"实测准确率"口径），否则阈值体系会自相矛盾。

**一个已知的部署张力（Laya 大幅缓解）**：Kev 需要 Python 3.12+/3.13 + uv + transformers≥5.17 + 常驻服务，且 4B 模型要 32GB 内存。而 **Laya 只要约 1GB 内存、CPU 可跑**——如果要给非技术用户装，Laya 是唯一现实的选择。

**借鉴 memoir 的三个设计**：
1. **每条路径独立失败**：capture / 注入 / 整理三条线互不阻塞，各有 escape hatch
2. **幂等初始化**：store 不存在就自动建，不报错
3. **失败可恢复**：模型不可用时保留已接收事件与失败结果；显式选择规则轨道可以独立运行，不伪装为同一次 Jev 成功或静默降级

## 12. 数据飞轮：判断日志 → 标注 → 微调本地模型

### 12.1 核心思路

**先让 Jev 跑一段时间积累真实判断记录，再用这些记录微调本地模型（Laya / Kev）。**

这条路成立，而且比"人工造数据"好得多——因为它是**分布内**的。合成数据的分布是假的，真实使用产生的分布才是真的。

### 12.2 为什么必须从第一天就记（时间敏感性）

**判断日志一旦漏记，事后无法重建。** 因为：

- 训练数据需要的是「**当时的 state + 当时的问题 + 当时的答案**」三元组
- `state` 是**当时的上下文**（那几轮对话、那批候选记忆）——过期就没了
- 你**无法**从最终落盘的那条记忆倒推回当时喂给模型的完整输入

而这个日志**不需要额外开发量**：判断层本来就要发请求、收响应，顺手记下来即可。**这是本设计里性价比最高的一笔投入。**

### 12.3 记什么

| 字段 | 内容 | 为什么 |
| --- | --- | --- |
| `state` | 完整原始输入 | 训练数据的输入侧 |
| `questions` | 当时的题型 + 选项 + criteria | 训练数据的指令侧 |
| `answers` | **完整概率分布**（不只是选中的那个） | 保留分布才能做校准拟合；只存标签会丢掉一半信息 |
| `backend` + `model_version` | 哪个后端、哪个版本 | 版本漂移时能区分（**别名会变，必须记版本号**） |
| `confidence` | 原始置信度 | 用于后续统一语义 |
| `downstream` | 这个判断的结果：自动落盘 / 进 `pending` / 被人改过 | 这是**标签质量的线索** |
| `human_verdict` | 人工 review 的最终裁决（如果有） | **这就是真值标签** |

### 12.4 标注的两个层级 ⭐️

这是最容易出错的地方——**不能把 Jev 的输出直接当标签。**

| 层级 | 来源 | 质量 | 量 | 用途 |
| --- | --- | --- | --- | --- |
| **预标注** | Jev 的输出 | ⚠️ 可能含错 | 大 | 省人力打底 |
| **真值标注** | **人工裁决** | ✅ 可信 | 小 | 校验 + 关键样本 |

**为什么不能直接用 Jev 输出当标签**：

1. Jev 自己也有位置偏差和校准问题（同一个判断在不同选项顺序下会变）
2. Jev 的 `confidence` 同样不可信（这是决策模型品类的通病）
3. **直接用 Jev 输出训练，Laya 学的是"Jev 的行为分布"而不是"正确答案分布"——误差会累积**

**但蒸馏本身没问题**，只要明确目标：**Laya 的目标是在相同任务上逼近 Jev 的准确率，同时本地免费**。这是**保真度（fidelity）**问题，不是超越问题。要超越，就必须引入人工真值。

→ **策略：Jev 预标注打底 + 抽样人工校验 + pending 队列的人工裁决作真值。**

### 12.5 staging 队列的双重身份 ⭐️

设计里本来就有的 `pending` / `contradict` 状态 + staging 目录，**同时也是训练数据管道**：

```
Jev 判断
   ├─ 高置信 → 自动落盘 ──────────────→ 预标注样本（量大，质量中）
   └─ 中低置信 → staging 人工 review ──→ 真值样本（量小，质量高）
                      ↑                          │
                      └──── 微调 Laya 后接管 ←────┘
                             （自动化率提升 → staging 队列变短）
```

**「人工 review 关口」和「训练数据管道」是同一个东西的两个视角。** 这意味着：

- 人工 review 不是纯成本，它在**生产训练数据**
- 随着 Laya 微调后接管，staging 队列会变短——**人工投入递减**
- 这正是 [evaluation.md](evaluation.md) 里 `Auto-Rate@ε` 想量化的那个趋势

### 12.6 从日志到训练数据

**好消息：不需要格式转换器。** 因为判断层的接口本来就是 `state + questions → answers`，而训练数据需要的正是「`state` + `questions` + `label`」——**同一套结构**。

现成工具：
- **Laya 官方 Kaggle notebook**：造数据 → RLCD 训练 → 温度拟合 → 评测，全流程
- **`kev-finetune` skill**（若走 Kev 路线）：含 `extract_workload.py`（可扫代码提取真实工作负载）、`convert_data.py`、`plan_size.py`

### 12.7 别忘了微调后的必做动作

训练样本按原始场景和来源与 calibration/test 隔离；正式测试输入及其派生判断日志不得回流训练。Jev 预标注和人工裁决分别记录来源，不因进入日志就成为独立真值。只复核低置信度队列会形成选择偏差，仍需对自动执行样本随机抽查。

1. **重新拟合温度**（校准）——微调会破坏原有校准，出厂温度不再适用
2. **重新校准阈值**——阈值是在旧模型的校准曲线上选的
3. **在冻结的 test 集上验证**——不能只看 dev 集

### 12.8 时间线

| 阶段 | 时间尺度 | 动作 |
| --- | --- | --- |
| v0.1 | 第 1 天起 | 开判断日志（**不能拖**） |
| 积累期 | 数周～数月 | 正常使用，日志自动累积；人工 review pending 队列产真值 |
| 第一次微调 | 积累够 300–500 条高质量样本后 | 微调 Laya，与 Kev 对比 |
| 迭代 | 持续 | 微调后接管判断层 → 自动化率上升 → staging 变短 → 新数据继续喂 |

**关于"够不够"的判断**：不设固定天数门槛。参考两个实证——DuoMem 用 teacher 轨迹蒸馏把 4B 从 4.3% 拉到 77.9%；`kev-finetune` 的实测案例是 **1050 条数据、15 分钟训练、67.7% → 73.6%**。所以**几百条就是一个可验证的起点**。

### 12.9 这个飞轮的研究价值

后续可研究**将使用中的人工 review 队列作为持续标注管道**，用风险—覆盖率与实际复核工作量检验系统是否改善。这需要额外的纵向实验和独立测试集，不作为首篇静态评测已经证明的结论。首篇范围见 [evaluation.md](evaluation.md) §11。
