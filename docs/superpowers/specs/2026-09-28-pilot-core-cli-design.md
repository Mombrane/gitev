# gitev 先导原型设计：独立核心库与 CLI

日期：2026-09-28；配置边界更新：2026-10-04。状态：整体设计已确认；用户确认提供 LLM 与 Jev，首版通用 LLM 只支持 OpenAI Responses API。基线：`423d846`。本次交付为设计文档，代码、数据标注和模型实验尚未开始。

本文细化 [评测方案](../../evaluation.md) 与 [交付计划](../../delivery-estimate.md) 中的先导阶段；[架构总览](../../design.md) 保留完整产品方向。先导预计 4–6 人日，包含在完整报告的工作量内，不包含正式全量评测和论文交付。

## 1. 目标与已确认范围

先验证三件事：维护操作能否被清楚标注；执行器能否正确应用与重放操作；规则、LLM、Jev 三种判断方式能否在相同条件下比较质量和成本。

- 使用独立核心库与薄 CLI；评测直接调用同一个核心库。
- 单用户、一个本地记忆仓库，包含个人范围和一个项目范围。
- 编程与日常生活同时覆盖，分别报告结果。
- 先构造场景，再人工确认预期行为；先导样例不作为后续论文的 locked test。
- 60 条意图样例：编程 30 条、生活 30 条。
- 24 个生命周期序列：编程 12 个、生活 12 个。
- 交付维护闭环、三种判断适配、判断日志、CLI、行为测试及先导报告。

暂不纳入完整 Agent 插件、常驻服务、多设备同步、多用户权限、向量服务、通用知识图谱、本地 Laya / Kev 适配、微调及自由生成式自动整理。保留后续扩展所需的原始判断记录，不为这些阶段预建框架。

## 2. 架构选择

| 方案 | 优点 | 取舍 |
| --- | --- | --- |
| 独立核心库 + CLI（采用） | 维护语义集中，可重放、可替换判断器；便于评测与后续宿主接入 | 先定义事件和操作契约 |
| 文件 + Skill 驱动 | 较快接入现有 Agent，适合体验实际工作流 | 行为受宿主影响，隔离评测较难 |
| 常驻服务 + API | 便于多个客户端与后台任务接入 | 增加服务部署和生命周期管理，不属于本次范围 |

实现语言沿用前期建议，选 Python；CLI 只负责输入解析、调用核心库和输出格式，不包含第二套维护逻辑。依赖选型与逐文件任务在实施计划中落定。

```text
自然语言输入 → 事实/维护意图抽取 ─┐
人工确认的结构化事件 ───────────┤
                               ↓
                    作用域过滤与候选检索
                               ↓
                     规则 / LLM / Jev
                               ↓
                        变更提案与策略
                               ↓
                  确定性校验 → 完整 Git 提交
                               ↓
                 当前事实 / 冲突提示 / 历史查询

评测程序调用同一条路径，逐步断言、记录费用与失败。
```

### 2.1 职责边界

| 组件 | 输入与输出 | 负责 | 不负责 |
| --- | --- | --- | --- |
| 抽取器 | 对话 → 原子事实与维护指令 | 保留主体、时间、作用域及来源片段 | 直接修改记忆 |
| 候选检索 | 查询或新事实 + 已提交快照 → 候选 ID 与内容 | 范围过滤、关键词匹配、稳定排序 | 根据未来事件挑候选 |
| 判断器 | 事件与候选 → 操作建议、目标、概率与依据 | 可替换的语义判断 | Git 写入、跳过应用策略 |
| 执行器 | 提案 + 当前版本 → 已应用或待审结果 | 合法转移、引用、幂等、版本检查 | 再实现一套模型推理 |
| 存储 | 条目、事件、提案 → 已提交快照与历史 | 完整提交、读取、重建与恢复 | 决定哪条语义事实正确 |
| 评测器 | 场景与配置 → 逐项结果和汇总 | 重放、断言、统计、成本与日志 | 将标准答案泄漏给被测系统 |

这些是模块职责，不要求分别做成服务或复杂插件系统。

### 2.2 模型服务与配置

首版由用户提供通用 LLM 和 Jev 两种模型服务。独立 CLI 不自带模型，也不自动读取 Codex、Claude Code 等宿主的模型配置或凭据。

| 服务 | 最小配置 | 用途 |
| --- | --- | --- |
| 通用 LLM | `base_url`、`model`、`api_key` | 自然语言事实/意图抽取，以及评测中的 LLM 判断对照组；首版可共用同一配置 |
| Jev | API Key；使用其独立接口与适配器 | 记忆维护判断及相应评测 |

通用 LLM 首版只支持 [OpenAI Responses API](https://developers.openai.com/api/docs/guides/migrate-to-responses) 请求与响应协议，不要求服务由 OpenAI 托管。`base_url` 表示 API 根地址（含服务需要的版本前缀，如 `/v1`），请求其下的 `/responses`，使用 `model` 与 `input`；不自动切换到 Chat Completions 或其他协议。Jev 不受此协议选择约束。

先采用非流式、单次自包含请求，由核心库提供本次可见上下文，不依赖服务端会话历史。模型输出经过本地结构校验后才能形成事实或提案；拒绝、未完成响应、缺失文本或结构无效均按处理失败记录，不能当成空事实或低置信度判断。具体请求字段和解析契约在实施计划中落定，并用真实服务的小批调用验证兼容性。

确认的结构化事件可绕过 LLM 抽取；因此只运行结构化输入的 Jev 维护轨道时不要求 LLM 配置。自然语言摄入和 LLM 对照评测必须有 LLM 配置。读取历史等不调用模型的命令不要求模型凭据；需调用模型但缺少配置时明确报错，不静默降级。

凭据通过环境提供，不写入记忆仓库或实验日志。评测记录所用模型、协议、非敏感配置及实际返回版本；缺失的版本或用量信息标为未知，不假定兼容服务提供全部元数据。后续宿主集成可以由宿主抽取后传入结构化事件，本次不实现宿主配置自动复用。

## 3. 数据模型

只设三种业务对象：输入事件、记忆条目、变更提案。调用日志和评测 manifest 是运行记录，不增加另一套事实源。

### 3.1 输入事件

事件保存稳定的 `event_id`、来源标识与内容哈希、发生时间、接收时间、作用域、原始内容。对话输入另保留说话者及消息位置，避免把用户陈述、他人转述和工具观察视为同一证据。

事件处理状态与每个候选的结果分开：事件可为收到、处理完成或处理失败；处理完成时，候选结果可同时包含已应用、待审和忽略。CLI 返回逐项结果及计数，不用一个成功标记掩盖混合结果。

相同事件 ID、相同内容再次提交时返回已保存的处理结果；同 ID 不同内容报输入冲突。失败事件使用同 ID 重试，保留尝试记录，不重复应用已生效变更。调用方没有提供 ID 时由系统生成并返回；重试需要复用它。

### 3.2 记忆条目

| 信息 | 设计约定 |
| --- | --- |
| 身份 | 独立 `memory_id`，不使用 taxonomy 或内容作为唯一键 |
| 作用域 | `personal` 或带项目标识的 `project`；本次只配置一个项目 |
| 主体 | 事实描述的是谁或什么；先导使用明确主体，不建设通用实体图谱 |
| 内容 | 一条可独立变化的自然语言事实，保持必要条件和上下文 |
| 状态 | `active`、`patched`、`superseded`、`contradict`、`expired`、`archived` |
| 时间 | 记录时间；事实需要时另记有效时间或到期条件，不把录入时间当事实生效时间 |
| 来源 | 事件及原文片段引用；更新保留原来源和新增变更来源 |
| 关系 | 有需要时记录取代、被取代及冲突关联，不因同类就合并 |

“住在杭州，喜欢清淡饮食”拆成两条；搬家不影响饮食偏好。分类和编程/生活标签用于检索辅助或评测分组，不代表作用域。跨项目的开发偏好可属于个人范围。

主体或作用域无法确定时，不自动覆盖已有条目。条件相同的事实才进入关系比较；项目约定优先于适用的个人默认，但不使个人默认失效。

### 3.3 变更提案

提案记录提案 ID、触发事件、基准快照、目标条目、操作、新内容、来源依据、判断器及策略版本。语义判断返回的概率原样保存；不把不同后端的 confidence 直接当成统一正确率。

提案状态为 `pending`、`applied` 或 `rejected`。`pending` 不是记忆状态，不隐藏原有效条目。原始判断与后续人工裁决分别记录。

同一事件可以产生多个提案。它们对同一事实存在依赖或相互冲突时，不按模型数组顺序逐条覆盖；先整理成一致的事件结果，不能解决的部分留待审。

## 4. 操作与执行策略

判断器统一建议以下操作：`new`、`duplicate`、`update`、`supersede`、`contradict`、`retract`、`expire`。无须长期保存且不含维护指令的输入记为忽略。人工裁决属于 review 事件，不伪装成模型自动判断。

| 操作 | 应用条件与结果 |
| --- | --- |
| 新增 | 主体、作用域和来源明确，门控允许后创建 `active` 条目 |
| 重复 | 确认指向同一事实，保留 ID，更新出现记录，不新建一份 |
| 更新 | 同一事实的局部信息变化；保留历史，条目为 `patched`，当前视图仅含有效内容 |
| 取代 | 目标和取代依据明确；旧条目 `superseded`、新条目 `active`，双向关系同批提交 |
| 冲突 | 同作用域、主体及适用时间，且无法确定取代关系；明确识别后保留冲突双方和关联，进入裁决流程 |
| 撤回 | 明确指向已有事实后记为 `archived`，附撤回原因与来源；原来源重放不能恢复 |
| 过期 | 明确到期条件成立或环境证据证明失效，转为 `expired` |

“今天想吃火锅”不自动替换“平时偏好清淡”；“这个项目用 unittest”不覆盖个人默认 pytest；明确搬家陈述才可能取代同一主体的现居地址。

### 4.1 自动执行与待审

格式、作用域、证据、引用和合法转移由代码检查。模型判断只有同时通过这些检查和相应操作的校准策略后才自动应用。

不同操作分别校准，不先固定一个通用 0.9 阈值。没有可用校准结果的模型操作，默认生成待审提案；先导可在不应用的情况下记录判断并评价准确率。确定性规则能直接处理明确 ID 的撤回和显式到期条件，但仍须记录规则依据和策略版本。

自然语言中的“撤回之前那条”等模糊指令先解析目标；目标不唯一时待审。低置信度更新不改变原条目。若待审提案涉及潜在冲突，普通召回附不确定性提示，提案内容不作为已确认的新事实。

已确定存在冲突时，普通召回以冲突组呈现相关条目，不将其中一方默认为确定答案。这样区分“疑似冲突的待审提案”和“已识别、尚未裁决的冲突事实”。

### 4.2 人工 review

CLI 展示原事实、拟执行操作、新内容及依据，支持批准或拒绝。批准前检查基准版本及前置条件；条件变化时重新产生判断或刷新提案，旧批准不能自动授权已经变化的提案。

人工裁决有独立事件和来源标记。评测中的裁决来自预先编排的后续输入，不向模型暴露标准答案；自动轨道与人工辅助轨道分别运行、分别报告。

### 4.3 失败与重试

- 网络超时、限流、无效响应等记录为处理失败，不等同低置信度；不凭空生成一条可批准的语义操作。
- 执行前校验不通过时不改变当前事实，返回明确失败原因或可复核提案。
- 重试保留相同事件身份，记录新的尝试；一次 CLI 调用不无限重试，也不静默切换判断模型。
- 模型调用在写锁外进行；应用时再次校验基准快照。过期判断不能覆盖更新后的状态。
- 崩溃后可能需要继续处理已收到的事件；不依赖一次 CLI 进程永久存活。

## 5. Git 存储与可见性

使用独立的记忆仓库，不混入用户项目源码。条目采用 Markdown 与 frontmatter，事件和提案采用结构化记录，分别放入 `entries/`、`events/` 和 `proposals/`。这些是数据存储位置，不是本次文档阶段创建的代码目录。

输入事件先持久化接收记录，再进行模型调用。应用结果将本批条目变更、提案状态和事件处理结果作为一次完整提交；读者只读取已提交快照。接收记录的提交与应用结果的提交可以分开，但一次取代的新旧条目不得拆成两个可见提交。

写入串行化，版本检查覆盖从判断到应用的间隔。提交前崩溃时，当前已提交事实不变；提交已成功但返回前崩溃时，重试从事件处理结果恢复，不再次执行。实现必须采用隔离的变更准备方式并验证这两种情况，不能把逐文件写入工作区等同于原子提交。

Git 提交 ID 由已提交历史解析并返回，不要求条目在自身提交内容中存储该提交的哈希。源码或数据仓库存在未识别的手工修改时明确报错，不自动丢弃这些修改。

事件 ID 防止同一事件重复执行；来源标识用于防止被撤回内容通过新的摄入事件重新出现。先导先保证同一原来源及其明确副本的阻止，不宣称解决所有未知来源的语义改写。用户重新明确确认同一事实属于新的授权事件，需保留它与历史撤回的关系。

## 6. 召回与证据巡检

### 6.1 当前事实与历史

普通查询先限定作用域，再用关键词做粗召回。个人查询不自动混入项目私有事实；带项目上下文的查询可同时返回适用个人默认和该项目约定，明确标注更具体的约定。

`active` 和 `patched` 可作为有效事实返回；后者使用更新后的内容。`superseded`、`expired`、`archived` 不进入普通事实列表。冲突及待审提示使用独立字段返回，不通过“过滤全部条目”制造无冲突假象。

历史查询可查看旧值、来源及变更顺序。事实时间明确时据此说明何时有效；未知时只报告记录及变更时间，不推断历史有效期。显式历史读取与普通召回分开统计。

候选顺序用稳定规则确定并记录 ID。精排可切换，先导默认用基础检索定位维护问题，再在相同候选上比较精排。报告分别指出候选未召回、判断错误和执行错误；不预设固定候选数能消除位置偏差。

### 6.2 最小巡检

`inspect` 接收可注入的当前时刻和环境证据。先导使用可控的路径/配置检查及场景提供的观察，不让模型自行任意浏览环境。

到期时间或证据明确时才提出失效操作。文件检查无权限、工具报错、证据过时或缺失均不是“事实已经不成立”；保留原事实，记录检查失败或待复核。

## 7. CLI 契约

| 命令 | 核心输入 | 结果 |
| --- | --- | --- |
| `init` | 独立记忆仓库路径与项目范围 | 初始化可用仓库；重复初始化不破坏已有内容 |
| `ingest` | 对话或结构化事件、来源、作用域、判断配置 | 逐项已应用/待审/忽略/失败结果、事件与提案 ID |
| `recall` | 查询、作用域、数量限制及可选精排配置 | 有效事实、来源、冲突和待审提示 |
| `review` | 提案 ID，以及查看、批准或拒绝动作 | 当前提案或裁决结果；版本变化时要求重新审阅 |
| `inspect` | 时刻与环境证据 | 已应用失效、待复核和检查失败结果 |
| `history` | 记忆 ID 或事件 ID | 内容演变、来源、操作与提交 |
| `eval` | 场景、判断配置、运行目录 | 隔离重放、逐步结果、统计及费用 |

默认易读输出，同时支持 JSON。标准输出承载结果，诊断信息单独输出。输入或执行错误使用非零退出状态；正常待审不伪装成进程错误。发生混合结果时保留完整逐项结果，不只输出成功部分。精确参数名与退出码表在实施计划中统一。

默认操作就是摄入并按策略执行；另提供只产生判断/提案的模式用于先导诊断，其输出不能算作实际自动应用成绩。CLI 与库使用同一套校验和策略。

## 8. 数据与评测设计

### 8.1 构造与标注

先编写场景和每一步真实变化，再生成自然语言表述；每个场景另带结构化输入用于隔离评测。两种输入是同一基础场景的不同视图，不能算作两个独立样本。

| 数据 | 编程 | 生活 | 覆盖要求 |
| --- | --- | --- | --- |
| 意图样例 | 30 条 | 30 条 | 新增长期事实、应忽略的临时内容、维护指令及混合意图 |
| 生命周期 | 12 个序列 | 12 个序列 | 新增、重复、更新、取代、冲突、裁决、过期、撤回及交叉边界 |

交叉边界包括作用域差异、临时要求与长期偏好、待审期间发生新变更、原来源重放。每个序列保留事件时间、可见证据、当前有效值、允许及禁止召回、预期状态和来源关系。

先导采用中文自然语言场景，编程场景保留真实格式的英文标识符；这不构成中英跨语言能力验证。公开基准后续按各自语言和原始协议单独评测。

样例可由 AI 起草，但最终标签经人工确认；记录标注者、复核状态、分歧及裁决。无人复核的样例标为草稿，不能声称已完成人工验证或独立标注。先导不承担正式报告的数据规模与低风险保证。

### 8.2 隔离、端到端与人工辅助轨道

隔离轨道使用确认的结构化输入，测判断和执行；端到端轨道从自然语言开始，额外测抽取及候选构造。两条轨道的结果分别保存。

纯自动轨道统计系统自动处理及待审结果；人工辅助轨道另外重放预定 review 事件，衡量裁决后的可用性。人工答案不回填纯自动轨道。失败和不支持操作保留在结果中，不静默删除样本。

每个场景/判断器/轨道使用隔离仓库。时间由场景注入，系统只能看到当前步骤及过去事件；评测器持有标准答案，抽取器和判断器不可读取它。

### 8.3 对照与统计

规则、LLM、Jev 共用维护执行器、原始输入、作用域及候选构造规则；端到端轨道共用抽取配置。各系统根据自身历史构造候选，其状态分化保留为结果，不能强行用正确历史替换。

先导可在开发样例上探索阈值，并输出未应用的判断质量；配置定型后使用按基础场景分开的校准和验证样例。样本不足时不开放相应自动操作，也不宣称达到某个风险上界。先导用过的数据不进入正式 locked test。

按编程/生活、操作类别及轨道分别报告：操作判断、逐步状态和完整序列正确率、有效召回、失效召回、空结果、待审比例、失败率、人工裁决次数、费用与延迟。数量和分母随指标一并输出。

自动执行覆盖率以预先定义的可评测决策机会为分母；待审、失败不能通过从分母剔除来提高覆盖率。另报已自动应用决策的错误率，自动应用为零时该错误率为 N/A。端到端漏抽取单独计错，避免只统计成功生成的提案。

排列诊断分别改变候选证据顺序与答案选项顺序，同序重复用于区分自身波动。派生排列不增加独立场景数。先导以原始数量、错误分布和案例为主要解释，不从小样本给出稳定排名或 1% 风险承诺。

### 8.4 运行记录与预算

记录代码与数据版本、场景 ID、域、轨道、模型返回版本、prompt/策略版本、时刻、候选 ID、原始概率、提案及执行结果、重试、token、费用与延迟。

判断日志从首次模型接入开启。仅保存适合留存的输入及响应，凭据不进入记忆库、Git 或实验结果；对真实来源的留存要求在引入真实数据时另行确定。训练候选与 calibration/test 按来源隔离，测试的派生日志不得用于微调。

模型可访问性与单样例费用是执行前置条件，按环境配置读取凭据。先验证小批样例和预算，再扩运行量；额度或模型不可用时记录阻塞项，不用模拟响应声称已经完成三模型实测。

## 9. 验收与行为测试

| 验收项 | 通过依据 |
| --- | --- |
| 原子事实及作用域 | 搬家不改变饮食偏好；项目约定不覆盖个人默认；主体不混淆 |
| 幂等 | 同事件重复输入结果一致，不重复创建条目或应用操作；同 ID 不同内容报错 |
| 待审可用性 | 低置信度提案不隐藏有效事实；可见冲突有提示 |
| 完整提交 | 取代后的旧、新条目及引用同时可见；不存在可读的半完成状态 |
| 失败恢复 | 提交前中断保持旧快照；提交后返回前中断，重试不重复应用 |
| 版本变化 | 判断期间或人工待审期间发生更新，旧提案不能覆盖新状态 |
| 撤回 | 目标明确时失效；原事件或原来源重放不恢复；新的明确确认另留依据 |
| 证据巡检 | 到期/有效环境证据触发预期操作；缺证据和检查失败不误判过期 |
| 当前与历史 | 当前只读有效内容；历史展示旧内容、来源及已知时间边界 |
| 隔离与日志 | 各运行仓库隔离；模型看不到未来事件和标准答案；失败及费用可查 |
| 模型接入 | Responses 请求与响应正确处理；拒绝、未完成和无效结构不写入事实；结构化 Jev 轨道可不配置 LLM；自然语言和 LLM 对照缺配置时报错 |

先导最终交付：可运行核心与 CLI、60 条意图与 24 个序列及人工复核记录、上述行为测试、三判断器实测结果、可重算的汇总、含失败案例的先导报告。

工程不变量的确定性测试必须全部通过。语义准确率不要求满分，必须如实报告；Jev 胜出不是验收条件。只有模拟测试通过、缺失人工复核或尚未接入真实模型时，应明确标记完成范围。
