# gitev：记忆维护评测与研究方案

修订日期：2026-09-28。研究资料核实于 2026-09-23，本次与仓库 `e1e7411` 的 Laya 后端及判断日志设计对齐。当前仍处于设计阶段；以下数据规模、实验设计和验收条件是计划，不是已完成工作或实验结果。

## 1. 研究目标与贡献边界

研究问题是：在持续接收新事实、修正、撤回和环境证据的过程中，记忆系统能否正确维护当前知识，并以可接受的成本决定哪些变更可以自动执行。

gitev 以 Git 保存记忆及变更历史，用确定性执行器落实维护操作，并比较规则、生成式 LLM 和专用决策模型 Jev 三种判断方式。Git 提供一个可检查的实现载体；判断是否准确、校准是否可靠、存储能否安全恢复，都需要分别验证。

计划形成三项交付：

1. 一组带逐步预期结果的维护场景，检查当前事实、历史依据、召回行为和操作失败语义。
2. 一个可以替换判断器、重放事件、重建结果的参考实现。
3. 关于维护正确性、自动处理覆盖率、成本及位置敏感性的实证分析。

不预先声称“首个记忆维护基准”“全新的自动化指标”“Jev 必然优于 LLM”或“Git 比向量存储更准确”。研究贡献最终由与先行工作的差异及实验结果决定。

## 2. 相关工作与可复用部分

| 来源 | 已覆盖的能力 | 本研究的使用方式 |
| --- | --- | --- |
| LongMemEval | 长期交互记忆，包含知识更新等能力 | 验证维护策略对外部问答任务的影响 [1] |
| ForgetEval | 取代、遗忘与清除等维护操作，提供模板和对抗用例 | 复用语义相容的测试；逐项说明不支持的操作 [2] |
| MEME | 多实体与演化记忆，包含依赖传播、失效认知和删除后的状态 | 用于确定研究边界；完整依赖传播评测放入扩展阶段 [3] |
| Selective prediction | 风险与覆盖率的权衡 | 作为自动处理率和拒绝决策的统计基础 [4] |
| MemoryData | 多种记忆方法和基准的统一运行入口 | 先验证适配成本，再决定是否接入；不作为核心引擎的前置依赖 [5] |

MemoryData 当前 README 将 LongMemEval 工具列为 sidecar，不能仅凭 preset 数量推定所有目标实验已经可以一键运行。mem0ai/memory-benchmarks 当前主要支持 Mem0 Cloud/OSS，接入 gitev 仍需适配；一期不维护两套完整 harness。[5][6]

自建数据集聚焦这些来源尚未满足本项目需要的组合：逐步状态断言、变更待审时的可用性、补丁后的有效视图、外部证据驱动的失效，以及撤回后旧来源重放。不能把这些组合的价值扩大为“既有研究完全不测维护”。

## 3. 研究问题与实验边界

| 问题 | 对照方式 | 主要观察 |
| --- | --- | --- |
| RQ1：显式维护机制能否减少错误复用，且不明显损失有效记忆？ | 同样的抽取器、检索器和回答模型，比较启用维护与仅追加记忆 | 失效内容召回、有效记忆召回、错误抑制、任务正确率 |
| RQ2：专用决策模型能否改善维护判断的质量—成本权衡？ | 同一执行器内只替换规则、LLM、Jev 判断器 | 操作正确率、风险—覆盖率曲线、成本、延迟 |
| RQ3：结论在哪些条件下不稳定？ | 候选排列、候选数量、重复请求、长序列、关闭巡检 | 翻转率、错误类型、维护成本和性能退化 |

RQ1 与 RQ2 为论文主线；RQ3 作为边界分析。Git 的贡献主要通过历史重建、提交一致性和恢复测试证明，不由问答分数推断。

## 4. 第一阶段实现范围

实现单用户、单项目、单本地记忆仓库的研究原型。支持命令行或库调用完成录入、判断、应用变更、召回、巡检和历史读取。网络模型调用放在写锁外，提交前校验基准版本；写入串行化。

先导采用独立核心库 + CLI，编程与日常生活同时覆盖，先构造场景再人工确认。60 条意图按两类各 30 条、24 个生命周期序列按两类各 12 个分配，分别报告结果。具体契约见 [先导原型设计](superpowers/specs/2026-09-28-pilot-core-cli-design.md)。

核心路径：会话或结构化事件 → 候选事实与维护指令 → 判断器 → 变更提案 → 确定性校验与应用 → 当前记忆视图及 Git 历史 → 召回。

一期不包含完整 Agent 插件、多设备同步、多人协作、可视化管理界面、本地模型微调或自由生成式全自动整理。需要验证的最小巡检以显式时钟和环境证据为输入，可由评测程序调用。

### 4.1 在编码前固定的语义

| 对象或行为 | 约定 |
| --- | --- |
| 记忆身份 | 使用独立 `memory_id`；taxonomy 是分类属性，不是唯一键；记录作用域 |
| 新增事实与维护指令 | 分开识别；“撤回之前的偏好”必须能触发操作，不能因不新增事实而被忽略 |
| 待审变更 | `pending` 属于提案状态；提案尚未生效时，不把原有效条目隐藏 |
| 取代 | 新旧条目与双向引用形成一次完整提交；读者只读取已提交版本 |
| 补丁 | 明确当前有效字段与变更历史；普通召回只输出当前有效值 |
| 冲突 | 先检查作用域、时间和明确修正关系；真正未解冲突不输出未经裁决的单一事实 |
| 过期 | 有到期规则或可核实的环境证据才失效；时间久、证据缺失或检查失败只触发待复核 |
| 重复与撤回 | 事件可幂等重放；撤回后再次输入原来源不得使旧事实复活；新的明确授权另作事件 |
| 溯源 | 记录触发事件、相关条目、证据引用、模型及策略版本、操作结果与提交 ID |

召回区分“当前事实查询”和“历史查询”：历史上曾成立的内容，可以在明确的历史问题中返回。不能把所有旧值都算作错误召回。

业务失效和物理擦除具有不同语义。本研究原型保留 Git 历史，因此不把“不再参与普通召回”称作彻底删除；ForgetEval 中需要物理清除的操作应单列不支持，不得计为通过。

### 4.2 不由模型决定的工程约束

合法状态转移、标识符引用、作用域检查、事件幂等和 Git 提交一致性由代码验证。语义或证据不足时记录待审提案；模型超时、无效响应等记录为处理失败，可按相同事件身份重试，不伪装成语义不确定。两类情况均不能通过未验证变更覆盖当前记忆。

测试必须覆盖：重复事件、两次并发更新、应用中途失败、重启恢复、取代链引用断裂、旧来源重放，以及完整历史重建。测试通过只证明这些明确条件下的实现行为，不等于线上可靠性已验证。

## 5. 数据设计：两份标注集及其派生测试

下列规模用于排期；先导实验后按覆盖不足与区间宽度调整。扩充规则在正式测试前固定，不依据哪个模型领先来决定。

| 数据资产 | 先导规模 | 首版报告目标 | 独立样本单位 |
| --- | --- | --- | --- |
| 写入与维护意图集 | 60 条 | 约 400 条 | 原始对话场景 |
| 生命周期集 | 24 个序列 | 约 120 个序列，每个 4–8 个事件 | 完整事件序列或共享模板的场景簇 |
| 排列测试 | 从先导数据抽取 | 从冻结场景派生 6 种排列；必要时穷举较小集合 | 仍为原始场景，不是排列数 |
| 长程测试 | 少量重放 | 从冻结场景派生 50/200 事件轨迹 | 基础场景簇，不把重复扩展当作新证据 |

意图集同时标注“是否有需保存的新事实”与“是否有需执行的维护指令”。至少覆盖闲聊、临时要求、长期偏好、推测、转述、明确修正、撤回，以及含多个意图的轮次。难负例目标不少于 30%，这是压力测试分布，不能直接当成真实线上分布。

生命周期场景包含：新增、重复、取代、局部更新、未解冲突、人工裁决、证据驱动过期、撤回。另对低置信度、跨作用域和来源重放做交叉覆盖，不做“七种状态乘所有操作”的机械笛卡尔积。

每个序列记录初始记忆、按序事件、模拟时刻、可见证据及每一步的预期当前值、关系、允许召回和禁止召回。涉及“简洁偏好与本轮详细要求”时，必须明确持续时间与作用域，不能默认二者冲突。

### 5.1 标注与划分

1. 先制定标注规则和歧义裁决规则，再编写数据。LLM 可起草样例，不作为最终标签裁判。
2. 第二位人工评审者独立复核全部正式 test 标签及至少 20% 的其他数据；记录裁决前一致率、类别分歧和裁决理由。
3. 按原始场景、模板及来源分组划分 dev/calibration/test，目标比例 40%/20%/40%；语义改写、排列和长程派生版本随基础场景分组。
4. 公布数据来源、许可、生成方法、校验规则、版本与 checksum。保留一部分由未参与实现者编写的 test 场景，以检查对自身设计的偏好。
5. 这一级规模支持初步对比和失败分析，不能支撑细粒度类别的稳定排名或 1% 风险保证。需要更强结论时增加独立场景。

## 6. 评测分为两条独立路径

**隔离评测：** 直接输入人工确认的结构化事件与候选记忆，固定其他环节，只检验判断与执行。由确定性断言检查状态和可见性，避免用另一个 LLM 判 Git 字段对错。

**端到端评测：** 从自然语言会话开始，包含抽取、候选检索、判断、写入、查询和回答。系统只能看到该时刻之前的内容，不能提前摄入未来修正。标准化事件由独立判定器映射到预期语义；自由文本问答采用原基准协议，并人工抽查一致抽样的结果。

两条路径分别报告。给正确候选后的高判断准确率，不能代替候选召回率或端到端维护正确率。

## 7. 指标及统计方法

| 维度 | 必报指标 | 防止误读的配套指标 |
| --- | --- | --- |
| 写入门控 | 条目级 Precision/Recall、每轮错误写入数 | 无输出比例、维护指令识别率 |
| 维护操作 | 逐步正确率、完整序列通过率、分操作混淆矩阵 | 有效事实被错误隐藏的比例、冲突漏检率 |
| 召回 | 有效事实 Recall@k、失效事实召回比例 | 空结果比例、当前/历史查询分别统计 |
| 自动执行 | 风险—覆盖率曲线、固定阈值下覆盖率与错误率 | 分操作结果、错误率区间、未处理比例 |
| 概率质量 | 多类别 Brier、可靠性曲线 | ECE 的分桶定义、每桶样本量 |
| 稳定性 | 排列翻转率、同序重复翻转率 | 候选数量敏感性、概率及排名变化 |
| 可追溯性 | 成功重建操作依据的比例 | 悬空引用、无法重建的提交、恢复失败数 |
| 系统代价 | 摄入/判断/巡检/召回/回答的调用数、token 和费用 | p50/p95、重试率、缓存条件、总墙钟时间 |

`Stale Retrieval Rate` 定义为当前事实查询中返回的失效条目数除以返回条目总数；无返回时该查询为 N/A，同时计入空结果比例。另报告“至少一次返回失效条目的查询比例”，避免单个查询返回很多条目扭曲结果。它必须与有效事实召回率共同解释。

`Auto-Rate@ε` 使用既有 selective prediction 的覆盖率解释。[4] 对冻结策略，在阈值 τ 下：

```text
coverage(τ) = 自动应用的决策数 / 全部可评测决策数
risk(τ)     = 自动应用中错误的决策数 / 自动应用的决策数
```

阈值在 calibration 集选择；test 只报告该阈值的 coverage、risk 和区间。若 test 风险未满足目标，明确报告“未达到目标”，不重选阈值后把结果当独立验证。无自动决策时 risk 为 N/A，coverage 为 0。

将 5% 和 10% 作为初版探索目标；1% 仅在样本量足够时讨论。固定策略、独立同分布且零错误时，单侧 95% 二项上界为 `1 - 0.05^(1/n)`；需要约 299 个自动决策样本才能降到 1% 以下。同序列事件、排列副本及反复挑阈值不能直接套用这一结论。校准不自动构成真实分布下的风险保证。

Brier 使用完整类别概率分布，注明采用各类别平方误差之和后取样本均值；不把任意 confidence 或重要性分数当作正确概率。LLM 若只提供自报置信度，要披露这一差异。普通 ECE 用预测类别概率和实际正确性计算。

模型对比采用配对的场景簇 bootstrap，报告 95% 区间；长序列以轨迹所属场景簇抽样。多个随机运行不增加独立 test 场景数。小样本结果不作“无差异”或“已达安全标准”的强推断。

## 8. 对照实验与最小实验矩阵

内部系统固定抽取器、候选构造、存储和回答模型：

| 配置 | 唯一主要差异 | 用途 |
| --- | --- | --- |
| A：仅追加 + 普通检索 | 不执行语义维护 | 衡量维护机制整体作用 |
| B：规则维护 | 使用显式修正词、精确匹配及到期规则 | 低成本参照 |
| C：LLM 维护 | LLM 输出同一组允许的操作 | Jev 的主要质量与成本对照 |
| D：Jev 维护 | 专用决策模型输出操作与概率 | 待验证方法 |
| E：一个外部开源系统 | 使用其原生维护路径 | 检查结论的外部适用性，暂以 Mem0 OSS 为候选 |

A–D 用于控制变量分析；E 是整体系统比较，不能把与 E 的差异全部归因于判断模型。隔离实验共享已确认的候选事实；端到端实验共享抽取器配置，但每个系统根据自身已形成的历史构造候选，状态分化是评测对象的一部分。

所有有自动处理阈值的内部方法都在 calibration 集获得相同调优预算。用同等风险水平比较覆盖率，用相同任务协议比较总成本；不直接比较未经校准的数值阈值。

| 实验 | 范围 | 首版是否必做 |
| --- | --- | --- |
| 自建意图集与生命周期集 | A–D；支持随机调用的方法目标 3 次运行 | 是 |
| 判断器替换 | B/C/D，固定维护执行器与候选构造 | 是 |
| 维护与巡检消融 | 关闭维护；仅关闭证据巡检 | 是 |
| 排列与候选数量 | 6 种排列与 2/5/10 个候选；同序重复对照 | 是，作为隔离诊断 |
| LongMemEval-S | A–E；先做 dev 冒烟，最终冻结协议运行完整 500 题 | 是，预算须先导测量 [1] |
| ForgetEval | C/D/E 的语义相容部分，披露完整操作支持矩阵 | 是，支持子集结果不得称为官方全套分数 [2] |
| MEME、LoCoMo、MemoryAgentBench | 根据论文主张新增 | 后续扩展 |
| 本地 Laya / Kev、微调、多个外部系统 | 新的研究变量 | 后续扩展 |

不把所有模型、数据集、排列、阈值和消融做全组合。完整外部基准首先执行冻结配置的一次正式运行；其余随机重复优先用于内部主实验。报告这一复现强度的限制，不把一次运行的 bootstrap 当作模型跨运行稳定性。

排列诊断拆开改变证据顺序和答案选项顺序，并以稳定候选 ID 对齐结果；候选数量实验另行改变集合组成。不用补无关候选的方式假装消除了数量敏感性。六排列平均首先是诊断方法，是否上线使用由实测收益和延迟决定。

## 9. 运行协议与成本预算

每个 case 使用隔离存储；正式运行记录代码 SHA、数据哈希、划分版本、模型返回版本、prompt 哈希、阈值、种子、候选 ID、事件时序、操作结果、重试及超时。

判断日志从接入 Jev 时开始记录，沿用 [架构设计 §12](design.md#12-数据飞轮判断日志--标注--微调本地模型) 的后续训练路线。保留脱敏后的可复现输入、完整概率分布、标签来源和人工裁决；Jev 输出只能作为预标注。训练候选数据、校准数据与 locked test 按来源隔离，正式测试输入及其派生日志不得回流训练。

提取、判断、检索、回答和评分分别记录费用。远程模型若不能固定底层版本，记录运行日期并承认活体复现限制。保存允许公开的原始响应，可用于指标重算；这不等价于重新调用模型的复现。

先导样本用于估计每项实验的总量：

```text
实验费用 = Σ(输入 token × 输入单价 + 输出 token × 输出单价)
         + embedding/检索服务费用 + 计算资源费用
预算      = 预计实验费用 + 预先约定的重跑余量
```

外部长上下文摄入、回答和评分可能比 Jev 判断更贵。计价日期、货币及实际价格写入 manifest；未测量之前不承诺固定金额。模型评分的费用属于评测成本，单独报告，不能混入实际系统使用成本。

使用完整官方数据或明确标记的子集；不能把重新标注或修改后的 LoCoMo 等数据仍称为原版基准分数。明确检索 token 预算、截断策略、回答模型与评分器，并报告不支持操作和运行失败，不默默丢弃。

## 10. 完成标准与论文证据

首版报告应包含：系统与执行边界图、数据覆盖表、维护操作结果表、风险—覆盖率曲线、成本—质量图、消融结果、外部任务结果，以及覆盖成功和失败的案例分析。所有数字从保存的结果自动生成。

完成条件：

- [ ] 维护语义、作用域和合法转移已冻结，确定性不变量及恢复测试通过。
- [ ] 两份数据集完成规定的人工复核、分组划分和版本固定。
- [ ] 规则、LLM 和 Jev 在同一执行器中跑通，调优预算可查。
- [ ] 正式实验有原始结果、失败记录、统计区间及成本明细。
- [ ] 外部基准适配的语义损失和不支持能力已公开说明。
- [ ] 图表可从原始结果重建，干净环境能完成小规模复现。
- [ ] 研究结论与证据对应；未支持的假设保留为负面或不确定结果。

若 Jev 未体现优势，可如实讨论其适用边界；若只有确定性测试通过，仍不足以支持跨场景研究结论。Git 可追溯性也不能替代有效记忆质量。论文是否有足够实质贡献需要在先导和正式实验后各评估一次。
