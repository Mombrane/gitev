# gitev · 评测方案设计

> 2026-09-23 ｜ 第一期交付内容之一
> 前提：gitev 同时是**研究性项目**，评测不是为了"跑个分"，而是为了**验证设计假设、驱动迭代、支撑对外比较**

---

## 0. 一句话结论

现有基准覆盖的是"**记忆好不好用**"（能不能召回、能不能答对），但几乎不覆盖"**记忆维护得对不对**"（状态流转是否正确、冲突有没有消解、过期有没有清理）。

而后者正是 gitev 的核心。所以评测方案必须分两条腿：**现成基准做横向对比**，**自建数据集验证核心设计**。三份自建数据集是第一期就交付的。

---

## 1. 先划清边界

| 能力 | 现有基准覆盖 | gitev 要做什么 |
| --- | --- | --- |
| 长对话事实回忆 | ✅ LoCoMo / LongMemEval | 直接跑，做基线 |
| 多会话推理、时间推理 | ✅ LongMemEval | 直接跑 |
| 选择性遗忘 | ✅ MemoryAgentBench（四能力之一） | 直接跑 |
| 测试时学习 | ✅ MemoryAgentBench | 直接跑 |
| **写入门控（该不该记）** | ❌ **无公开数据集**（只有方法论文自带的评测） | ⭐️ **自建** |
| **状态机流转正确性** | ❌ 无现成基准 | ⭐️ **自建** |
| **决策模型的排列鲁棒性** | ❌ 无 | ⭐️ **自建** |
| **校准 + 误差预算自动化率** | ⚠️ 有 ECE/Brier，但无"自动化率"命名指标 | ⭐️ **自建指标** |
| **git 后端** | ❌ 现有 harness 的预设全是向量 / 图 / KV | ⭐️ **写一个 preset 接进 MemoryData** |

> 这张表右边那一列，就是 gitev 的研究贡献点。**"维护得对不对"这一块是公认的评测盲区**——不是我们没找到，是确实还没有。

## 2. 五层评测体系

评测对象要按系统架构分层，否则出了错不知道是哪一层的问题。

| 层 | 评什么 | 核心指标 | 数据来源 |
| --- | --- | --- | --- |
| **① 抽取层** | 该不该记（写入门控） | Gate Precision / Gate Recall / **污染率** | ⭐️ 自建「写入门控集」 |
| **② 判断层** | 分类准不准、冲突判定对不对、概率可不可信 | Classification Acc / Transition Acc / **ECE / Brier / Auto-Rate@ε** | ⭐️ 自建「状态流转集」+「排列鲁棒性集」 |
| **③ 召回层** | 找不找得到、排序对不对 | Recall@k / MRR / nDCG@k / Answer F1 | ✅ 现成基准（LoCoMo / LongMemEval） |
| **④ 维护层** | 长期用下来会不会变脏 | **Stale Retrieval Rate** / Day-N Recall / 可追溯率 | ⭐️ 自建「状态流转集」的长程变体 |
| **⑤ 系统层** | 端到端表现 + 代价 | 任务成功率 / 每轮 token / 召回延迟 p50·p95 / 每次判断成本 | ✅ 全部基准 |

**为什么要单列「判断层」和「维护层」？** 因为这两层是 gitev 相对现有系统的差异所在。如果只跑端到端任务成功率，判断层判错了会被上层掩盖——你只看到分数低了，不知道是抽取问题、判断问题还是召回问题。

## 3. 现成基准怎么用（已核实存在）

| 基准 | 规模/状态 | 测什么 | 怎么用 |
| --- | --- | --- | --- |
| **LoCoMo**<br>`snap-research/locomo` 1183★ | 每对话平均 300 turns、9K tokens、至多 35 sessions | 长对话记忆：QA、事件总结、多模态对话 | 改造后可用。**注意它的"写入"是隐式的，需要显式化**才适配我们的写入门控评测 |
| **LongMemEval**<br>`xiaowu0162/LongMemEval` 1102★，**ICLR 2025** | 500 题；S 档 ~115k token、M 档 ~1.5M token | **五种能力**：信息抽取 / 多会话推理 / 时间推理 / **知识更新** / 拒答 | **直接可用**。其中「知识更新」子集最贴近状态机语义 |
| **MemoryAgentBench**<br>`HUST-AI-HYZ/MemoryAgentBench` 459★，**ICLR 2026** | 把长上下文数据集改造成多轮增量形态 | **四种核心能力**：准确检索 / 测试时学习 / 长程理解 / **选择性遗忘** | **直接可用**。论文自己指出：**没有现有基准覆盖全部四种能力**——这给我们留了空间 |
| **MemoryData**<br>`OpenDataBox/MemoryData` 148★ | 统一套件，4 大基准族（MemoryAgentBench / LoCoMo / LongBench / MemBench）+ 22 个方法预设 + 单一入口 + 统一结果 JSON | 多系统横向对比 | ⭐️ **作为 harness 基座**。预设全是向量/图/KV，**我们要写一个 git + 决策模型的 preset 接进去** |
| **memory-benchmarks**<br>`mem0ai/memory-benchmarks` 113★ | 开源评测套件，支持本地 Ollama 运行 | 多系统对比 | 作为第二个 harness 交叉验证，避免"只在自家 harness 上跑得好" |
| `OpenDataBox/awesome-agent-memory` 58★ | 按四轴整理的论文清单 | 文献索引 | 持续跟踪入口 |

**选用策略**：以 **MemoryData 为主 harness**（它已经统一了多个基准族和 22 个方法预设，我们只需加一个 preset），用 **mem0ai/memory-benchmarks** 做交叉验证。

## 4. 三份自建数据集 ⭐️ 第一期交付

这三份是评测方案的核心，也是研究贡献所在。

### 4.1 写入门控集（Write-Gate Set）

**评什么**：给定一段对话轮次，系统该不该产出记忆条目？

**为什么必须自建**：现有基准把"写入"当隐式步骤，不评对错。但实际上**写错比漏写代价大得多**——漏记一条只是下次要重新问，错记一条会永久污染记忆库、拉低所有后续召回的精度。

**怎么建**：种子直接来自 `memoir` 的 prompt-harness 用例（13 个，我读过源码），它已经把边界写成了可执行用例：

| 该捕获（正例种子） | 不该捕获（难负例种子） |
| --- | --- |
| 架构 / 设计决策 | 工具调用及其输出 |
| going-forward 规则（"以后都用 X"） | 礼貌用语、闲聊 |
| 项目事实 | 常规问答（问了答了，双方都没学到新东西） |
| 用户偏好声明 | **混合了规则和动作的轮次**（无法归类） |
| 多事实轮次 | **撤回**（retraction——用户收回了之前说过的话） |
| 跨命名空间的事实 | 只针对本轮的临时反馈 |

**注意"撤回"这个用例**：它直接关联状态机——用户收回一个说法，系统不该记，或者该把已记的标记为失效。这类边界现有基准完全没有。

**规模目标**：v0 阶段 100–200 条（含至少 30% 难负例），人工标注；后续扩到 500+。

**指标**（见 §5.1）。

---

### 4.2 状态流转集（Lifecycle Set）

**评什么**：给系统一串有先后关系的写入事件，检查最终的记忆状态是否正确。

**这是最没有现成参照的一份**，也是最能验证 gitev 设计的一份。

**构造方法**：按状态机的七种状态设计场景，每个场景是一个**有序事件序列**：

| 场景类型 | 事件序列示例 | 期望结果 |
| --- | --- | --- |
| **取代** | 写入"项目用 MySQL 8.0" → 写入"我们已迁移到 PostgreSQL" | 旧条目 → `superseded`，新条目 → `active`，且旧条目有 `superseded_by` 指向新条目 |
| **补丁** | 写入"项目用 MySQL 8.0，端口 3306" → 写入"端口改成 5432 了" | 旧条目 → `patched`，保留原值 + 追加变更记录（不是全量替换） |
| **冲突** | 写入"用户偏好简洁回复" → 写入"用户要求详细解释" | 双方 → `contradict`，进 pending 队列，**不自动裁决** |
| **重复** | 写入"用 ruff 做 lint" → 写入"lint 工具用的是 ruff" | 不新建条目，只更新已有条目的 `last_seen` |
| **过期（有写入事件）** | 写入"当前用 Jev 云端 API" → 写入"已切换到本地 Kev" | 旧条目 → `superseded` |
| **过期（无写入事件）** ⭐️ | 写入"配置文件在 ~/.config/x" → 时间推进 + 环境变化 | 巡检后 → `expired` |
| **裁决** | 人为裁决一条 `contradict` 条目 | 胜者 → `active`，败者 → `superseded`，记录裁决理由 |
| **撤销** | 写入一条 → 用户明确撤回 | 条目失效（不能装作没发生过，要留痕） |

**倒数第二类（无写入事件的过期）特别重要**——它验证的是"状态机必须配巡检"这个设计判断。如果只跑有写入事件的场景，会误以为状态机够了。

**指标**（见 §5.2、§5.5）。

---

### 4.3 排列鲁棒性集（Permutation Set）

**评什么**：同一个判断，在不同候选顺序下结论稳不稳？

**为什么必须建**：决策模型有实测确认的**位置偏差**——同一批证据放在选项首位和末位，结果会变；反转选项顺序能让分类概率从 0.84–0.89 跳到 0.93–0.96。更严重的是**候选数量也会改变结论**：加入一个无关选项后，已有选项的对数 odds 从 +0.38 掉到 +0.11（10 组实验全部下降）。

这意味着：**如果不测这个，你的精排结果可能是排序的产物，而不是相关性的产物。**

**怎么建**：对每条测试用例，穷举或随机采样 N 种候选排列，记录每次的输出。

**指标**（见 §5.4）。

## 5. 指标定义

### 5.1 写入门控 —— 用不对称代价

| 指标 | 定义 | 为什么要它 |
| --- | --- | --- |
| Gate Precision | 写入的条目中真正该记的比例 | **主指标**——错记代价高 |
| Gate Recall | 该记的条目中被写入的比例 | 次要 |
| **污染率** | 单位轮次内的错误写入条数 | 直接反映记忆库变脏的速度 |
| 沉默正确率 | 在"本不该产出任何记忆"的轮次上正确沉默的比例 | 验证"沉默是默认"这条设计 |

**关键：不要只看 F1。** 因为两类错误的代价不对称——应该报告**加权代价**，权重体现"错记 vs 漏记"的代价比。

### 5.2 校准

| 指标 | 定义 | 用途 |
| --- | --- | --- |
| **ECE** | 按置信度分桶，算 \|准确率 − 置信度\| 的加权平均 | 判断 confidence 能不能当阈值用 |
| **Brier Score** | 概率预测的均方误差 | 综合衡量概率质量（越低越好） |
| **Reliability Curve** | 置信度 vs 实际准确率的曲线 | 可视化诊断；配 ECE 一起看 |
| **Skill Score** | (B_ref − B_actual) / B_ref，用基线 Brier 作参照 | 相对提升的标准化度量 |

**为什么必须测校准**：决策模型返回的 `confidence` 字段**不是正确率**，它只是概率分布集中度的算术摘要。实测表明高置信度错误是存在的。所以阈值必须建立在**实测的校准曲线**上，而不是假设上。

### 5.3 Auto-Rate@ε（自建指标）⭐️

**定义**：在允许 ε 的错误预算下，系统可以**自动执行而不需人工复核**的决策占比。

$$\text{Auto-Rate}@\varepsilon = \frac{|\{d : \text{conf}(d) \ge \tau_\varepsilon \ \wedge\ \text{acc}(\text{conf} \ge \tau_\varepsilon) \ge 1-\varepsilon\}|}{|D|}$$

其中阈值 $\tau_\varepsilon$ 从校准曲线上选，使得该置信区间内的实际准确率 ≥ 1−ε。

**为什么需要它**：这是唯一能同时回答"**准不准**"和"**能省多少人工**"的指标。ACE 高说明概率可信，但不说能自动化多少；准确率高也不说高置信区间的可用比例。

**这个指标没有现成的命名标准**（检索确认），是个空白——可以从 gitev 的评测里提出来，作为方法论贡献之一。

**报告格式**：给一组 ε（1% / 5% / 10%），分别报告 Auto-Rate。对比对象是"全部人工复核"（Auto-Rate = 0）和"全部自动"（Auto-Rate = 1，但错误率失控）。

**实证参照（Laya 已发布的实测数据）**：

| 覆盖率 | 准确率 |
| --- | --- |
| 接受全部判断 | 83.8% |
| 只接受置信度前 80% | 89.4% |
| 只接受置信度前 50% | **92.2%** |

> 丢掉一半低置信判断，准确率从 83.8% 提到 **92.2%**。这就是 Auto-Rate@ε 想量化的东西，而且给出了一个可比的参照点。

**⭐️ τ 不要拍，从成本矩阵推**：Laya 的 act/escalate 决策头用这样一张成本表——

| 情况 | 奖励 |
| --- | --- |
| 自动执行且正确 | +1.0 |
| 自动执行且错误 | **−3.0** |
| 升级给人工 | −0.5 |

策略**自动学出"置信度 ≥62.5% 才行动"**。注意那个 3:1 的成本比——**错误代价是人工代价的 3 倍**，这与本项目「宁可留脏不可错删」的第一原则同源。建议我们沿用这个做法：**把 τ 定义成成本比的函数**，而不是手工试出来的数。

**⚠️ 前置条件**：算这个指标之前，必须先统一 `confidence` 的语义。不同后端、甚至同一后端的不同原语之间定义都不一致（`choice` 用熵、`noul` 用 `max(p,1−p)`，同一个判断能报出 0.53 和 0.90 两个值）。详见 [research.md](research.md) §6.5。

### 5.4 排列鲁棒性

| 指标 | 定义 | 阈值建议 |
| --- | --- | --- |
| **Flip Rate** | 不同排列下最终答案发生翻转的用例比例 | 越低越好；> 10% 说明精排结果不可信 |
| **ΔProb（概率方差）** | 同一候选项在不同排列下的概率标准差 | 用于诊断是"轻微抖动"还是"结论级翻转" |
| **顺序敏感度** | 概率与候选位置的相关系数 | 用来决定是否需要做位置校准 |

**处理方法**（学术界的标准做法）：
1. **多次随机排列求平均** —— 报告均值 ± 方差，而不是单次结果
2. **位置交换过滤** —— 对同一对候选做正反两次判断，只保留一致结论，或取平均
3. **穷举排列诊断** —— 小规模用例穷举所有顺序，用卡方 / Cramér's V 量化位置偏差
4. **配对检验** —— 对比两个方案时用配对 bootstrap 置信区间

### 5.5 维护层

| 指标 | 定义 |
| --- | --- |
| **Transition Accuracy** | 状态流转结果符合预期的用例比例 |
| **Supersede Precision** | 判为"取代"的案例中真正是取代关系的比例（误判会导致有效记忆被埋） |
| **可追溯率** | 每次状态转移都能从 git 历史还原出"何时、被谁、以何依据"的比例 |
| **Stale Retrieval Rate** | 召回结果中包含已失效条目的比例 ⭐️ |
| **Day-N Recall** | 经过 N 天 / N 轮模拟后，仍能正确召回的比例（长程稳定性） |
| **维护成本** | 每次巡检消耗的 token / 调用次数 |

**`Stale Retrieval Rate` 是维护层的核心指标**——它直接回答"用久了记忆库会不会变脏"。这正是现有基准不测的。

### 5.6 成本与延迟

| 指标 | 说明 |
| --- | --- |
| 每轮 token 消耗 | 捕获 + 注入的固定开销 |
| 召回延迟 p50 / p95 | 交互式体验的硬约束 |
| 每次判断的 API 成本 | 用来论证"判断层换成本地模型"的收益 |
| 单条记忆的全生命周期成本 | 写入 + 多次召回 + 巡检的摊薄成本 |

## 6. 方法论纪律（六条）

这些是让评测结果**可信**的前提，缺一条就会变成自说自话。

| # | 纪律 | 具体做法 |
| --- | --- | --- |
| 1 | **dev / test 分离** | 用 development 集调阈值和 prompt；test 集**只读一次** |
| 2 | **冻结 + checksum** | 数据集版本和文件哈希写进 manifest，改动必须留痕 |
| 3 | **锁定测试（locked test）** | 选定最终方案前不碰 test 集；读了就记录 |
| 4 | **消融实验** | 逐个关掉组件看贡献：去掉判断层 / 判断层换 LLM / 关状态机 / 关闭巡检 / 不同候选数 |
| 5 | **多次随机排列** | 所有涉及决策模型的判断，跑 N 次随机排列报告均值 ± 方差 |
| 6 | **配对 bootstrap 置信区间** | 对比两个方案时不能只比单点数值，要报区间 |

**第 4 条特别重要**：因为没有消融，你无法回答"加了判断层到底有没有用"这个核心问题。消融的设计应该是：

| 配置 | 目的 |
| --- | --- |
| 全量（判断层 + 状态机 + 巡检） | 完整系统 |
| 去掉判断层（纯规则） | 判断层的净贡献 |
| 判断层换成 LLM | 与"直接调大模型"对比成本和准确率 |
| 去掉状态机 | 状态机对长期记忆质量的影响 |
| 去掉巡检 | 验证"状态机必须配巡检"这个判断 |
| 关掉排列校准 | 位置校准的收益 |

## 7. baseline 对比对象

没有 baseline 的评测没有意义。至少要有这五组：

| baseline | 说明 | 目的 |
| --- | --- | --- |
| **无记忆** | 纯上下文，不带任何历史 | 下界 |
| **全量上下文** | 把所有记忆条目塞进 prompt | 证明"检索 + 判断"比"全塞"更好 |
| **朴素 RAG** | 向量检索 top-k，无判断层 | 最直接的对照 |
| **同架构 + LLM 判断** | 抽取、判断都用 LLM | 验证"决策模型做判断层"是否划算（准确率 vs 成本） |
| **现有开源系统** | mem0 / A-MEM 等，用 MemoryData 跑 | 横向定位 |

`同架构 + LLM 判断` 这一组是最关键的——它直接回答"为什么要引入决策模型"这个设计决策到底成不成立。

## 8. 评测驱动的改进闭环

评测不是一次性动作，要能形成回路：

```
设计假设
   ↓
跑评测（dev 集）→ 看分层指标定位问题
   ↓
是抽取问题？判断问题？召回问题？维护问题？
   ↓
针对性改进（调 prompt / 调阈值 / 调状态机规则 / 调候选数）
   ↓
回归评测（确保没弄坏别的）
   ↓
方案冻结 → 跑一次 test 集 → 记录结果
```

**关键设计**：因为阈值要用 dev 集校准，所以**每次改判断层（比如换模型版本、做微调）都必须重新校准阈值**——否则 dev 集上好看、test 集上崩。

## 10. 这套评测的可发表性

评测方案本身有可发表的部分，主要在三处：

1. **「写入门控」的公开数据集** —— 检索确认目前**没有**公开的"该不该记"标注集，只有方法论文自带的评测。填补空白。
2. **「状态流转」的评测方法** —— 把记忆的状态机语义（取代 / 补丁 / 冲突 / 过期 / 撤销）形式化成有序事件序列的评测，现有基准只沾到边（MemoryAgentBench 的选择性遗忘、知识更新类基准的"更新对"构造法）。**尤其是区分"有写入事件的过期"和"无写入事件的过期"**，这点没见人测过。
3. **Auto-Rate@ε 指标** —— 把"误差预算下能自动化多少决策"形式化，兼顾准确率与人工节省。检索确认无现成命名标准。

**定位**：不是"又做了一个记忆系统"，而是"**提出了一套评测记忆维护能力的方法**"，并用 gitev 作为参考实现。这个定位比单纯报分数更有价值——因为维护能力的评测是公认的空白。
