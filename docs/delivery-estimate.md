# gitev：从零实现、评测到 arXiv 技术报告的工作量

修订日期：2026-10-05；下列数值保留 2026-09-28 原范围估算。状态：从零开始的研究交付计划，尚未实现、运行实验或提交论文。本文配套 [评测方案](evaluation.md)，估计均为项目规划判断，不是实测工时；已考虑现有 Laya / Kev 后端和判断日志路线。

## 1. 推荐目标与估算结论

2026-10-05 已加入 [读写时机与本地多范围设计](superpowers/specs/2026-10-05-memory-lifecycle-scope-design.md)。原估算基于较小的单项目范围，不直接覆盖本次增量；以下人日与日历表是历史规划基线，当前范围的新总工期尚未估算。先确认新版契约、验证多范围发布与恢复，再依据小批工作重估。完整 hooks、常驻服务及跨电脑同步仍后置。

推荐完成一篇聚焦“可追溯的记忆维护，以及决策模型的质量—成本权衡”的实证技术报告。交付包括最小参考实现、两份人工复核数据集、对照与消融、公开基准结果、可重算图表和英文稿件。

原单项目范围从零开始，预计 **30–45 人日净工作量**；增加约 20% 返工余量后，按 **36–54 人日**规划。1 人日按约 8 小时有效工作计，这是人员投入总量，已经假定熟练使用 AI 辅助编码、测试、实验脚本和初稿写作。AI 不替代最终标签裁决、实验决策和论文结论核验。

主要负责人全职推进、另有人提供少量独立标注复核时，日历计划约 **8–11 周**。两名互补成员全职投入时可争取 **5–7 周**，总人日通常不会减半。只有一个作者且无法安排独立复核，应披露单人标注局限，不声称完成双人标注。

完成终点是“可提交稿件和复现材料”。实际 arXiv 上线时间、背书等待和审核处理不包含在内，不能保证接收。

## 2. 原范围的三种路线

| 路线 | 交付 | 净工作量估计 | 用途与限制 |
| --- | --- | --- | --- |
| 可行性验证 | 最小维护引擎、60 条意图、24 个序列、规则/LLM/Jev 对照 | 4–6 人日 | 判断是否继续；样本规模不支撑完整论文主张 |
| 聚焦的实证报告（推荐） | 约 400 条意图、120 个序列、主要对照与消融、一个完整外部问答基准、维护基准相容子集、英文稿及复现包 | 30–45 人日 | 结论限定在测试分布，不承诺 1% 风险或全面领先 |
| 完整产品与扩展论文 | 在推荐范围上加入插件、多设备同步、自动整理、本地模型等 | 通常 60–90+ 人日 | 子项目较多，需分别设计后重估；不建议作为首篇报告前置条件 |

4–6 人日的可行性验证包含在推荐路线内，不额外叠加。推荐路线不覆盖完整 hooks 插件、多设备同步、管理 UI、本地 Laya / Kev 和微调。

## 4. 先导验证：原范围 4–6 人日目标

先导验证从 W1–W5 各取最小部分，不要求搭好所有架构：

1. 定义 8 类维护事件与 24 个短序列，明确每一步预期当前值。
2. 在临时 Git 仓库中实现新增、取代、待审和撤回的最小执行路径，验证重复事件和原来源重放。
3. 建 60 条自然语言意图样例，人工确认标签。
4. 对同一结构化输入比较规则、LLM 和 Jev，记录原始响应、错误、耗时和 token。
5. 在小批外部样例上验证适配与费用统计，估算完整运行成本。
6. 输出一页先导结论：标签是否稳定、错误集中在哪、模型是否可访问、预算是否可承担。

继续条件是问题可明确标注、引擎可检查、比较有足够区分度，且模型接入和费用可控。它不要求 Jev 必须获胜。

若 Jev 质量或覆盖率无优势，选择缩小其作用范围、如实研究失效条件，或者暂缓 Jev 主张。若不同评审者持续无法区分“冲突”和“更新”，先修改语义再扩数据。若所有方法都接近满分，应增加独立难例，并将先导样例固定为开发资料，不能继续当 locked test。

### 4.1 新增范围需要计入的工作

新增工作包括：稳定项目/设备身份与分支绑定、各范围快照组合、所有读取入口的范围检查、依赖版本变化校验、单范围发布故障验证、纯聊天及轮次/阶段处理、批次/恢复入口、分层读取预算与生命周期指标。先导 60/24 规模保持，覆盖矩阵和工程测试随范围更新。

上述工作并入 W1/W2/W4，模型与场景验证并入 W3/W5/W6；不能只按新增文档行数估工。真实宿主接入与同步需另外设计、估算及验证，不纳入本地模拟验收。

## 6. 数据和实验量意味着什么

400 条意图和 120 个序列的目标不是追求大数字，而是覆盖操作与边界。按每序列 6 个事件的中值，约有 720 个逐步事件检查点；它们仍只来自 120 个序列，统计时不能当成 720 个独立场景。

作为费用规划的简化示例，如果对全部 400 条意图和 720 个事件决策，以 4 个内部配置各跑 3 遍，会出现约 `1,120 × 4 × 3 = 13,440` 次逻辑判定。实际规则判断不调用模型，确定性配置也不必重复；dev 调优、排列和额外模型重试会增加调用。该数字是规模示意，不是正式 test 样本量。

外部 LongMemEval-S 的 500 题乘 5 个配置，产生 2,500 个回答结果，还要计入历史摄入、检索和评分；长上下文摄入可能成为主要费用。应在先导阶段记录单位样例成本和长尾，按实际模型价格推算，不根据 Jev 单次调用价格估整套实验。

排序与候选数量诊断只选冻结的诊断子集执行，不与全部外部基准做全组合。完整外部正式运行至少一次，内部模型主实验目标三次；这已经足够产生需要认真核查的一批结果。

不建议事先用“几百元肯定够”作预算。先计算摄入、判断、回答、评分的明细，再为重跑设上限；预算不够时公开缩小实验范围，同时收窄结论。

## 7. 从实验结果到论文

建议英文工作标题：**gitev: Evaluating Auditable Memory Maintenance with Decision Models**。标题和摘要在结果出来后调整，避免预先写成“更可靠”或“更高效”。

| 论文部分 | 必须回答的问题 | 所需证据 |
| --- | --- | --- |
| Introduction | 什么具体维护错误值得研究？ | 简明失败案例和有边界的研究问题 |
| Related Work | 相比 ForgetEval、MEME、LongMemEval、选择性预测新增什么？ | 逐项能力比较与原始引用 |
| Semantics and System | 什么是正确更新？模型与执行器各负责什么？ | 操作定义、有效视图、实现结构和恢复约束 |
| Evaluation Protocol | 数据如何产生、标注、隔离？如何保证公平比较？ | 标注手册、来源、split、预算和基线 |
| Results | 维护是否有用？Jev 的代价与质量如何？ | 主结果、风险—覆盖率、成本、区间 |
| Ablations and Failures | 收益来自哪一部分？在哪些条件下失败？ | 消融、排列诊断、逐类错误及案例 |
| Limitations | 结论不能推广到哪里？ | 样本、合成数据、单仓库、闭源模型与不支持操作边界 |
| Reproducibility | 别人怎样重建同一结果？ | 代码、数据、版本、响应与脚本 |

建议至少准备：1 张系统图、1 张覆盖矩阵、1 张主结果表、1 张消融表、1 张风险—覆盖率图、1 张成本—质量图，以及一组失败案例。图表数量是写作建议，不是 arXiv 的硬性要求。

有价值的结果可以是条件性的，例如“只在明确取代场景中降低成本，模糊冲突仍需要复核”。负面结果也可能形成实证贡献，但必须提供系统分析，不能仅把“没有提升”包装成创新。

不需要训练新模型才能完成这篇报告。若最终只证明 Git 提交可回放，而没有维护行为、比较方法或边界分析上的实质发现，论文贡献可能不足；不能用扩充篇幅代替研究内容。

## 8. 人员和 AI 如何分工

主要工程/研究负责人负责语义、架构、对照公平性、实验取舍和最终结论。数据复核者独立标注正式测试数据并参与歧义裁决；若两名全职成员合作，可由另一人主导数据与评测，避免全部围绕实现者的直觉出题。

AI 可辅助：实现适配器和测试、生成候选场景、检查结果 schema、统计脚本、图表与英文表达。人工必须负责最终标签、相关工作原文核验、失败解释、图表与原始数据核对。不能由同一个模型生成题目、给出标签并担任唯一评分器后，宣称得到独立验证。

推荐路线已经考虑 AI 辅助，不应再机械把总工期除以某个“AI 提效倍数”。自动生成的样例和代码越多，往往越需要明确抽查与复核边界。

## 9. 什么时候需要重估

| 变化 | 处理方式 |
| --- | --- |
| Jev 账号、固定版本或服务不可用 | 保留同接口，继续规则/LLM 与引擎工作；Jev 结论等待实际接入 |
| API 抖动、限流、成本超预算 | 记录失败；重排跑批或缩小并明确标注范围 |
| 需要证明 1% 风险上界 | 独立样本与校准工作明显增加，另行做统计设计 |
| 要完整 hooks 插件 | 初步额外预留 4–8 人日，具体取决于宿主兼容与异步可靠性 |
| 要本地模型部署或微调 | 新开工作包；本计划不包含硬件准备、训练和对比 |
| 要多设备同步或生产级物理删除 | 重新设计一致性及历史存储边界，不能按小补丁处理 |
| 要会议级 benchmark 论文 | 增加外部独立标注、更多系统、规模与泛化实验后再估算 |

## 10. arXiv 提交前的实际完成条件

arXiv 要求可供学术评价的科学贡献，并进行内容审核；其审核不等于同行评审。研究提案本身不能当成已经完成的研究报告。[A][B]

- [ ] 正文中的所有结果都有对应原始记录和重建命令。
- [ ] 结论、限制、外部基准子集和未支持能力写清楚。
- [ ] 代码与数据的公开授权、第三方材料引用已核对。
- [ ] 作者、署名、机构、摘要、分类和许可证由作者确认。
- [ ] LaTeX 源码及图表可干净编译，引用逐条核实。
- [ ] 作者提前检查账号及目标分类的 endorsement 状态；需要时自行完成背书流程。[C]
- [ ] 准备一份干净环境复现说明，区分缓存结果重算与重新调用在线模型。

建议在第 1 周就检查账号和背书条件，以免写完后才发现外部依赖。提交与公开发布另由作者执行或明确授权；本次交付仅为报告修订和工作量估算。

## 11. 本轮交付边界

本轮交付仅包含评测方案、工作量说明及配套文档同步；产品开发、收费模型实验和 arXiv 提交均未启动。下一步是先导验证及依据选定语言与目录形成逐文件实施计划。判断日志纳入参考实现，本地后端适配和微调继续作为后续阶段。
