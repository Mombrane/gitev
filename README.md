# gitev

> **Git 做存储，决策模型做判断** —— 给 AI Agent 的长期记忆系统。

---

## 这是什么

现有 Agent 记忆方案基本是两个极端：

| 路线 | 代表 | 优点 | 问题 |
| --- | --- | --- | --- |
| 向量库 | mem0、ChromaDB 方案 | 语义检索能力强 | 不可审计、不可追溯、写入不受控 |
| 纯 Markdown 文件 | 各类 `memory.md` 方案 | 可读、可版本化 | **没有任何判断能力**，越写越脏 |

gitev 走第三条路：**用 git 仓库做记忆的唯一事实源，用一个专门的决策模型做判断层。**

所谓"决策模型"（decision model），指的是 Jev 这类**不生成文本、只从给定选项里做选择**的模型——它读一次输入，对同一个输入并行回答多个结构化问题，返回带概率和置信度的答案。gitev 将验证它在记忆分类、判定和排序中的质量与成本；结构化输出不等于判断正确，速度、费用和稳定性都需要在本项目场景中实测。

---

## 要解决的问题

调研下来，现有开源实现在这条链路上**各缺一块**：

| 方案 | 会话捕获 | 记忆存储 | 写入判断 |
| --- | --- | --- | --- |
| claude-mem | ✅ 生命周期 hook 自动捕获 | ❌ SQLite + ChromaDB，不是 git | ✅ 靠 LLM 压缩 |
| gitmemo / agent-memory | ❌ 靠 SKILL.md 契约，Agent 自觉调用 | ✅ git 存 Markdown | ❌ 无判断，全凭 Agent 自己决定 |
| **gitev** | ✅ hook 自动捕获 | ✅ git 版本化 | ✅ **决策模型判断层** |

项目将「**决策模型 + git 记忆存储**」作为待验证的实现方案，不预先宣称该组合具有首创性。

---

## 架构

```
┌─ 捕获层 ─ Stop hook（async，不阻塞）────────────────┐
│  会话结束时：抽取候选事实 → 判断层 → 写进 git 仓库   │
├─ 注入层 ─ SessionStart hook ────────────────────────┤
│  会话开始时：注入记忆索引 + 库状态 + 待办提示        │
├─ 维护层 ─ Skill / Slash Command（agentic）──────────┤
│  按需：召回 / 手动写入 / 冲突消解 / 状态流转         │
├─ 整理层 ─ /dream 入口（手动 + 自动门）──────────────┤
│  周期性：巡检 / 整合 / 修剪（记忆的垃圾回收器）      │
└─────────────────────────────────────────────────────┘
              ▲          ▲          ▲
        ┌─────┴──────────┴──────────┴─────┐
        │  判断层：决策模型                │
        │  分类 / 冲突判定 / 相关性精排    │
        └──────────────────────────────────┘
```

判断层被单独抽出来，是因为四个层都要做判断，但判断类型不同、成本敏感度不同。抽出来之后它可以是云端 API，也可以是本地小模型。

---

## 三个设计要点

### 一、判断层只做选择，不做生成

决策模型不能写字，只能做选择。所以边界很清晰：

| 环节 | 谁做 |
| --- | --- |
| 从对话中抽取候选事实 | **LLM**（判断层做不到） |
| 归到哪个分类 | 决策模型（choice） |
| **与已有记忆是什么关系**（新增/重复/取代/更新/冲突） | 决策模型（choice） |
| **召回精排** | 决策模型（score + noul） |
| 整理时两两判冲突 | 决策模型 |
| 整合成文 | **LLM** |

目标是让 LLM 负责抽取与整合，将适合的结构化判断交给决策模型；是否降低成本、改善稳定性和可校准性，由对照实验决定。

### 二、状态机：永不删除，宁可留脏

记忆条目带状态：`active` / `superseded` / `patched` / `contradict` / `expired` / `archived`。`pending` 属于变更提案；待审提案不隐藏原有效条目。

三条铁律：

1. **保留可追溯历史** —— 业务失效通过状态表达，历史仍保留在 Git 中；这不代表物理擦除。
2. **低置信度不覆盖当前事实** —— 变更进入待审队列，原有效记忆继续可用；同时评估错误抑制与过期事实误用的代价。
3. **状态转移必须可溯源** —— commit message 写清触发源、判定结果、置信度。

对于没有新写入事件的环境变化，需要**基于环境证据的巡检**。经过时间只触发复核；缺少证据时不能让模型凭旧内容推定事实失效。

### 三、沉默是默认

从会话中抽取记忆时，**默认输出为空**。绝大多数对话轮次没有值得长期保留的内容，"什么都不记"是正确的、高质量的结果，不是失败。

只有在同时通过四道检查时才写入：这个事实一周后仍相关吗？未来会话真会受益吗？能从代码/git log 里发现吗？资深工程师会把它写进笔记吗？

## 评测

这个项目**同时是研究性项目**，所以评测不是附属品，而是第一期就要交付的内容——**没有评测集，状态机和判断层的对错就无法验证**（判断层的阈值必须从实测的校准曲线里选出来，不能拍脑袋）。

首篇报告聚焦两个问题：显式维护是否减少旧事实误用且保留有效记忆；在同一执行器下，Jev 相比规则与 LLM 能否改善质量—成本权衡。

| 路径 | 评什么 | 手段 |
| --- | --- | --- |
| 隔离评测 | 每一步维护操作与召回可见性是否正确 | 约 400 条意图样例、120 个生命周期序列，人工复核后冻结 |
| 端到端评测 | 从对话摄入到最终回答的表现 | LongMemEval-S 和 ForgetEval 语义相容的操作；明确不支持范围 |
| 稳定性诊断 | 排列、候选数量与重复请求的影响 | 从冻结场景派生，不能把排列数当作独立样本数 |

ForgetEval 和 MEME 已覆盖部分维护能力，本项目补充逐步状态、待审可用性、证据巡检和来源重放等场景。**Auto-Rate@ε** 沿用 selective prediction 的风险—覆盖率思路，不声称是新指标。相关资料和统计约束见 [评测方案](docs/evaluation.md)。

先以 **4–6 人日**完成先导验证，再进入完整研究原型和正式实验。从零到可提交的技术报告预计 **30–45 人日净投入**，含返工余量约 **36–54 人日**；完整插件、本地模型微调和多设备同步不在该估算内。详见 [交付计划](docs/delivery-estimate.md)。

## 数据飞轮：用真实使用喂出本地模型

本地模型（Laya / Kev）零样本都不可靠，必须微调——**而微调需要的数据，正好能用真实使用产生**：

```
Jev 跑判断 → 判断日志 ─┬─ 高置信 → 自动落盘 ──→ 预标注样本（量大，质量中）
                       └─ 中低置信 → staging 人工 review ──→ 真值样本（量小，质量高）
                                          ↑                        │
                                          └── 微调后的本地模型接管 ←┘
                                              （自动化率上升 → 人工队列变短）
```

三个要点：

1. **判断日志必须从第一天记。** `state` 是**当时的上下文**（那几轮对话、那批候选记忆），**过期就再也补不回来**——你无法从最终落盘的那条记忆倒推回当时喂给模型的完整输入。好在它不需要额外开发量：判断层本来就要发请求收响应，顺手记下来即可。
2. **staging 队列有双重身份。** 它既是人工 review 关口，**也是训练数据管道**。人工 review 不是纯成本，它在生产训练数据；而且随着本地模型接管，这个队列会越来越短。
3. **Jev 的输出只能当预标注，不能当真值。** 它自己也有位置偏差和校准问题，直接拿它当标签会让误差累积。所以：**预标注打底 + 抽样人工校验 + staging 的人工裁决作真值**。蒸馏的目标是**逼近 Jev**（保真），要超越就得靠人工真值。

第一版就要开日志——见 [docs/design.md](docs/design.md) §12。

### 后端选型：为什么本地首选是 Laya 而不是 Kev

| 后端 | 零样本可用性 | 部署门槛 | 定位 |
| --- | --- | --- | --- |
| **Jev**（云端，闭源） | ✅ 可直接用 | 只需 API key | v0.1 使用 |
| **Laya-421M**（本地，Apache-2.0） | ❌ 必须微调 | **约 1GB 内存，CPU 可跑** | **本地首选** |
| **Kev-4B**（本地，Apache-2.0） | ⚠️ 相对可用 | 32GB Mac 或 GPU | 本地备选 |

Laya 是 [NandhaKishorM/laya](https://github.com/NandhaKishorM/laya)（Convai Innovations，2026-09-18 开源，21k★），用 ModernBERT 双向编码器而非 decoder，参数小约 10 倍（421M vs 4B），标称延迟低一个数量级（38ms vs 721ms，注意两者测量硬件不同）。但要说清两件事：

- **延迟优势对我们的场景其实有限**——写入判断每次会话一次、巡检是离线的，都对延迟不敏感。它真正的价值在**部署门槛**（1GB vs 32GB，决定了能不能"装完就用"）和**解锁更高频的判断**。
- **"零样本不可用"不是否决理由**——官方自己写明它是 "a fast base to specialise, not a zero-shot decision engine"，但 **Kev 同样需要微调**。所以真正该问的是：*在"记忆判断"这个具体任务上，微调后的 Laya 和 Kev 谁更好？*

**这个问题的答案只能靠评测回答。** 所以路线是：v0.1 用 Jev 跑通链路并建立评测协议 → 用独立训练数据分别微调 Laya 和 Kev → 在相同冻结测试集上比较；测试数据及派生判断日志不得回流训练。

⚠️ 接入任何本地后端前有个前置动作：**先把 `confidence` 的语义统一**。不同原语的定义不一致（`choice` 用熵、`noul` 用 `max(p,1−p)`，同一个"一边 0.9 的二选一"能报出 0.53 和 0.90 两个值），不统一的话整个阈值体系会自相矛盾。详见 [docs/research.md](docs/research.md) §6.5。

## 值得提前知道的坑

这些是从实测和论文里挖出来的，直接影响判断层怎么调：

| 坑 | 具体表现 | 应对 |
| --- | --- | --- |
| **候选顺序会改变判断结果** | 同样的证据放在选项首位 vs 末位，正确率差别很大；反转选项顺序能让分类概率从 0.84–0.89 跳到 0.93–0.96 | 精排要做位置校准，部署前跑排列测试 |
| **候选数量会改变判断结果** | 加入一个无关选项后，已有选项的对数 odds 从 +0.38 掉到 +0.11（10 组实验全部下降） | 每次精排固定候选条数 |
| **`confidence` 字段不是正确率** | 它只是概率分布集中度的算术摘要，分布集中也可以是 confidently wrong。**更麻烦的是不同原语之间定义还不一致**（`choice` 用熵、`noul` 用 `max(p,1−p)`，同一个判断能报出 0.53 和 0.90 两个值） | 接入任何后端前先统一语义；阈值必须在自己数据上实测 |
| **长输入精度衰减** | 训练只覆盖短序列；输入变长后准确率显著下降 | 靠上游粗召回把候选集压小，别把全文塞进去 |
| **模型别名会漂移** | `jev-latest` 指向的版本会变，已校准的阈值随之失准 | pin 具体版本号 |
