# gitev

> **Git 做存储，决策模型做判断** —— 给 AI Agent 的长期记忆系统。

---

## 这是什么

现有 Agent 记忆方案基本是两个极端：

| 路线 | 代表 | 优点 | 问题 |
| --- | --- | --- | --- |
| 向量库 | mem0、ChromaDB 方案 | 语义检索能力强 | 不可审计、不可追溯、写入不受控 |
| 纯 Markdown 文件 | 各类 `memory.md` 方案 | 可读、可版本化 | **没有任何判断能力**，越写越脏 |

gitev 走第三条路：**用 git 仓库做记忆的唯一事实源，用一个专门的决策模型做判断层。**

所谓"决策模型"（decision model），指的是 Jev 这类**不生成文本、只从给定选项里做选择**的模型——它读一次输入，对同一个输入并行回答多个结构化问题，返回带概率和置信度的答案。这类模型比生成式大模型**更快、更便宜、更稳定**，而且输出 schema 有保证，天生适合做"分类 / 判定 / 排序"这类工作。

---

## 要解决的问题

调研下来，现有开源实现在这条链路上**各缺一块**：

| 方案 | 会话捕获 | 记忆存储 | 写入判断 |
| --- | --- | --- | --- |
| claude-mem | ✅ 生命周期 hook 自动捕获 | ❌ SQLite + ChromaDB，不是 git | ✅ 靠 LLM 压缩 |
| gitmemo / agent-memory | ❌ 靠 SKILL.md 契约，Agent 自觉调用 | ✅ git 存 Markdown | ❌ 无判断，全凭 Agent 自己决定 |
| **gitev** | ✅ hook 自动捕获 | ✅ git 版本化 | ✅ **决策模型判断层** |

而且「**决策模型 + git 记忆存储**」这个组合，目前开源社区**没有人在做**——两条线各自都有人走，但没有交集。

---

## 架构

```
┌─ 捕获层 ─ Stop hook（async，不阻塞）────────────────┐
│  会话结束时：抽取候选事实 → 判断层 → 写进 git 仓库   │
├─ 注入层 ─ SessionStart hook ────────────────────────┤
│  会话开始时：注入记忆索引 + 库状态 + 待办提示        │
├─ 维护层 ─ Skill / Slash Command（agentic）──────────┤
│  按需：召回 / 手动写入 / 冲突消解 / 状态流转         │
├─ 整理层 ─ /dream 入口（手动 + 自动门）──────────────┤
│  周期性：巡检 / 整合 / 修剪（记忆的垃圾回收器）      │
└─────────────────────────────────────────────────────┘
              ▲          ▲          ▲
        ┌─────┴──────────┴──────────┴─────┐
        │  判断层：决策模型                │
        │  分类 / 冲突判定 / 相关性精排    │
        └──────────────────────────────────┘
```

判断层被单独抽出来，是因为四个层都要做判断，但判断类型不同、成本敏感度不同。抽出来之后它可以是云端 API，也可以是本地小模型。

---

## 三个设计要点

### 一、判断层只做选择，不做生成

决策模型不能写字，只能做选择。所以边界很清晰：

| 环节 | 谁做 |
| --- | --- |
| 从对话中抽取候选事实 | **LLM**（判断层做不到） |
| 归到哪个分类 | 决策模型（choice） |
| **与已有记忆是什么关系**（新增/重复/取代/更新/冲突） | 决策模型（choice） |
| **召回精排** | 决策模型（score + noul） |
| 整理时两两判冲突 | 决策模型 |
| 整合成文 | **LLM** |

终态是让 LLM 只做"抽取"这一件不可替代的事，其余判断全部交给决策模型——**不只是省钱，更关键的是判断稳定性和可校准性**。

### 二、状态机：永不删除，宁可留脏

记忆条目带状态：`active` / `superseded` / `patched` / `contradict` / `pending` / `expired` / `archived`。

三条铁律：

1. **永不物理删除** —— 只改状态字段，正文留在 git 历史里，随时可翻回来。这是 git 存储相对向量库最大的优势。
2. **宁可留脏，不可错删** —— 判错的代价不对称：漏掉一条过期记忆只是检索质量略降，错删一条有效记忆是永久丢信息。所以低置信度**什么都不做**。
3. **状态转移必须可溯源** —— commit message 写清触发源、判定结果、置信度。

另外，状态机治不了"环境变了"型过期（没有写入事件来触发重判），所以**必须配定期巡检**。两者缺一不可。

### 三、沉默是默认

从会话中抽取记忆时，**默认输出为空**。绝大多数对话轮次没有值得长期保留的内容，"什么都不记"是正确的、高质量的结果，不是失败。

只有在同时通过四道检查时才写入：这个事实一周后仍相关吗？未来会话真会受益吗？能从代码/git log 里发现吗？资深工程师会把它写进笔记吗？

## 评测

这个项目**同时是研究性项目**，所以评测不是附属品，而是第一期就要交付的内容——**没有评测集，状态机和判断层的对错就无法验证**（判断层的阈值必须从实测的校准曲线里选出来，不能拍脑袋）。

评测分两条腿：

| 腿 | 评什么 | 手段 |
| --- | --- | --- |
| 横向对比 | 记忆好不好用（召回、推理、遗忘） | 复用公开基准：LoCoMo、LongMemEval、MemoryAgentBench，以 [MemoryData](https://github.com/OpenDataBox/MemoryData) 为统一 harness |
| **纵向验证** | **记忆维护得对不对**（状态流转、冲突消解、过期清理、写入门控） | ⭐️ **自建三份数据集** |

**为什么必须自建**：现有基准测的是"能不能召回、能不能答对"，但**几乎不测"维护得对不对"**。而后者正是这个项目的核心——现有 harness 的记忆后端预设全是向量 / 图 / KV，没有一个把 git 状态机当成被评测对象。

第一期交付的三份数据集：

| 数据集 | 评什么 |
| --- | --- |
| **写入门控集** | 这条信息该不该存进长期记忆（含 30%+ 难负例：工具输出、闲聊、临时反馈、**用户撤回**） |
| **状态流转集** | 一串写入事件后状态是否正确（取代 / 补丁 / 冲突 / 重复 / 过期 / 裁决 / 撤销）；**特别区分"有写入事件的过期"和"没有写入事件的过期"** |
| **排列鲁棒性集** | 同一判断在不同候选顺序下稳不稳（因为决策模型有实测确认的位置偏差） |

指标上除了常规的准确率 / ECE / Brier，还提出一个 **Auto-Rate@ε** —— 在允许 ε 错误预算下、系统可以自动执行而不需人工复核的决策占比。这个指标同时回答"准不准"和"能省多少人工"，目前没有现成命名标准。

详见 [docs/evaluation.md](docs/evaluation.md)。

## 值得提前知道的坑

这些是从实测和论文里挖出来的，直接影响判断层怎么调：

| 坑 | 具体表现 | 应对 |
| --- | --- | --- |
| **候选顺序会改变判断结果** | 同样的证据放在选项首位 vs 末位，正确率差别很大；反转选项顺序能让分类概率从 0.84–0.89 跳到 0.93–0.96 | 精排要做位置校准，部署前跑排列测试 |
| **候选数量会改变判断结果** | 加入一个无关选项后，已有选项的对数 odds 从 +0.38 掉到 +0.11（10 组实验全部下降） | 每次精排固定候选条数 |
| **`confidence` 字段不是正确率** | 它只是概率分布集中度的算术摘要，分布集中也可以是 confidently wrong | 阈值必须在自己数据上实测 |
| **长输入精度衰减** | 训练只覆盖短序列；输入变长后准确率显著下降 | 靠上游粗召回把候选集压小，别把全文塞进去 |
| **模型别名会漂移** | `jev-latest` 指向的版本会变，已校准的阈值随之失准 | pin 具体版本号 |
